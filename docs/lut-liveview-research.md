# 实时取景 LUT：Z30 C1.20 静态侦察

2026-11-04。目标是让 SD 卡上的 3D LUT 在即时取景中实时可见，并与拍摄结果一致。本轮只做静态侦察：没有访问相机，没有生成固件，没有改动现有功能。拍后套用 LUT 的研究与实现见 [lut-postprocess-research.md](lut-postprocess-research.md)。

## 路线判断

CPU 逐帧处理不作为主路线。LCD 约 720×480，即约 34.6 万像素；按 v7 内核每像素约 258 条指令，一帧约 8,900 万条，30 fps 需要每秒约 27 亿条。v6 单色卡死已经证明，同步占满 CPU 会饿死整机。每帧约 690 KB 的输出超过原厂缓存维护阈值 `0x45000`，会走 SVC 全缓存路径；显示缓冲的交接点也未恢复。

主路线是把 LUT 转换成原厂图像管线自身的色彩参数，由硬件实时执行。本轮的侦察都围绕“管线里有哪些可编程的色彩阶段”。

## 本轮发现

### 1. 原厂支持从 SD 卡加载自定义 Picture Control（NP3）

Picture Control 服务代码旁有字符串 `PICCON`（`0x1020F358`）、`B:\NIKON\CUSTOMPC\`（`0x1020F364`）和 `NP3`，以及版本串 `0100`、`0200`、`0210`、`0300`（`0x1020E21C`–`0x1020EE9C`）。`0x1020EFC6` 一带的扫描逻辑限制最多 30 个文件（`cmp #0x1e`）、1000 个条目（`cmp #0x3e8`）。

此前 `analysis/feature_research/imaging/FINDINGS.md` 检索 `.np3`、`.NCP`、`curve`，结论是“没有从 SD 卡导入曲线的实现”。这个结论不成立：那次检索没有命中，是因为固件里的字符串是不带点的大写 `NP3`。

意义：自定义 Picture Control 在取景、照片和视频中都由原厂实时应用。如果把 LUT 拟合成 NP3 能表达的参数，**不改固件**就能得到实时预览，代价是只能近似。

自定义槽的设置数据块为 0x248 字节（`0x1020CB00` 读取设置 ID `0x900`–`0x911`，缓存于 `0xC29214DC+0x60` 和 `0xC29229C4+0x60`，步长 `73×8`）。584 字节大约只容纳一条 257 点曲线（514 字节）加参数和名称，**推测 NP3 只带一条亮度/RGB 曲线，没有每通道曲线或 3D 表**。这是按容量推断，尚未从曲线编译代码确认。

### 2. 修饰单色引擎是“3×4 矩阵 + 257 点 1D 曲线”

第二轮提到的 index-6 状态里三段 `0x800` 表，内容已经解开（`0x1025F990`）：

| 地址 | 内容 |
| --- | --- |
| `0x106AD350` | 系数块，只有首项 256：Q8，只保留 Y 行（灰色模式） |
| `0x106AD370` | 系数块，第 0、4、8 半字为 256：Q8 的 3×4 单位矩阵（每行 3 个系数加 1 个偏移） |
| `0x106AD390` | 257 项 u16：0…256，Y 恒等曲线 |
| `0x106AE390` 起 | 每 `0x800` 一张，257 项。灰色为常数 128；棕褐色 Cb 约 115→122、Cr 约 139→133；其他变体与强度各一对 |

即：这个内存到内存的图像引擎先做矩阵，再用以 Y 为下标的 1D 曲线生成 Y、Cb、Cr。`0x800` 字节的槽位只用了 257 项，硬件可能支持更长的表，尚未证明。

它没有 3D 查表能力，但“矩阵 + 1D 曲线”正好是 LUT 近似拟合所需的形状。该引擎由描述图 `0xC1EEA800` 驱动，经 `0x1020182C` 入队，完成消息 `0x42183009`；`0x1020182C` 的 BL 调用者约 70 处，多数位于 `0x10243xxx`–`0x1026Bxxx` 的效果模块。

附带价值：拍后修饰路线如果改用这个引擎执行拟合参数，可以免去 CPU 3D LUT 的耗时，代价是精度。

### 3. 取景与拍摄是两套任务

初始化数据中的任务名（`0x1206B874`–`0x1206C71C`）：

- 拍摄：`IMPIIP0`、`IMPIIPW1`–`IMPIIPW9`、`IMPMIPU0/1`、`IMPSFLT`、**`IMPTM`**（推测为色调映射）、`IMPTRAN0/1`、`IMPJPGCO/EN`
- 取景：**`LVIIP`**、`LVMIPU`、`LVSFLT`、`LVVMAP`、`LVENC`、`LVSTCALC`、`LVDAFC/I`
- 驱动：`IPUDRV`、`IPUDRSEM`、`IPUSVEV0`、`IPUBFMU0`

命名推断：`IIP` 是 RAW 到 YCbCr 的显影管线，取景和拍摄各有一个实例。Picture Control 的色彩参数应当在 `IIP`（及拍摄侧的 `TM`）配置中下发。**这些角色都按名称推断，尚未追踪任务入口和配置结构。**

### 4. 已排除的线索

- `HueAdjustmentRed`、`Contrast2012`、`SharpenEdgeMasking` 等字符串（`0x101B83E0`）是 XMP/Camera Raw 风格的元数据名，不是 ISP 参数。
- `0x115CA558` 起每 0xB0 字节一条的记录是创意 Picture Control 的描述（ID `0x804`–`0x813`，内嵌名称），只含普通参数，不是色彩表。
- ROM 扫描到 86 段 257 点单调 u16 序列、4 段 1024 点；本轮没有发现 N³×3 形状的 3D 网格。扫描只是启发式，不能证明管线中不存在 3D 表。

## 第二轮：IPU 的 LUT 单元与取景前端 ISP 的表

### IPU 有一个 6 库 LUT 单元，但它不在逐帧取景路径上

IPU 单元表在 `0x1068B2C0`，共 42 项 `{MMIO 基址, 处理函数}`。31 号单元（`0x20100A40`）的处理函数 `0x1019F5CE(msg)` 从 `msg+0xC` 取配置块，在 `cfg+0xB0+8i`（i=0…5）读 `{字节长度, 指针}`，把 u16 表复制到 LUT RAM `0x24000000/2000/4000/1000/3000/5000`，每库最多 1024 项。6 个指针各自独立，硬件允许三通道各用不同曲线。

- 节点类型 0x11 就是这个色彩单元：通用图像服务的节点链 `0xC18EF2F8` 中，指向配置块 `0xC18EEF68` 的节点类型字节是 0x11。修饰单色（第一轮第 2 节）的矩阵也打包进类型 0x11 节点（`0x1025F520` 把 16 个 Q8 系数写入寄存器字），所以矩阵和曲线在同一个单元里。
- 通用图像服务 `0x100EDB0A` 让 0–2 库共用 `0xC18F6648`、3–5 库共用 `0xC18F6E48`：两张 1024 点表，10 位输入，输出 0…256（0→0、128→164、1023→256）。
- QEMU 辅助 StartLV 运行中，`0x20100A50` 只被写过一次（参数地址 `0xC18EEF68`）。运行后读回，6 组配对已填好：0–2 库都是 `0xC18EF3A8`，3–5 库都是 `0xC18EFBA8`，两者都是接近 sRGB 的 gamma，三通道共用。这一次作业属于通用图像服务，不是逐帧取景。断点设在 `0x1019F5CE` 也一直没有命中，执行路径尚未查清。

### 逐帧取景由前端 ISP（`0x2038xxxx`）完成

QEMU 运行中取景 ISP 共完成 333 批。前端寄存器由 `0x1011B674`–`0x1011E74A` 这段自动生成的逐字段写入代码配置，所有表都经 `0x1011E734(ctx, dst, src, len)` 上传，目标地址是 `dst + (ctx[4] << 18)`，即按实例号区分。StartLV 时写入的表：

| 区域 | 形状 | 推测用途 |
| --- | --- | --- |
| `0x20383900` 起，6 份 | 每份 103 字（约 206 点），单调上升、凹形 | gamma，可能是 3 通道 × 2 |
| `0x203842C0`、`0x20385134`、`0x2038533C`、`0x20385544`/`0x2038574C` | 129 字（257 点） | 色调曲线 |
| `0x20384A74` 等 4 份 | 65 点线性 | 中性的 65 点表 |
| `0x20385A5C`/`0x20385AE4` | 65 点，从 `0x800` 递减 | 增益曲线 |
| `0x20381F90` 起，8 份 | 每份 36 字节，`0x80` 为中性 | 36 段（每段 10°）的色相/饱和度调整 |
| `0x20385C00` | 512 个 u8，递增 | 映射表 |
| `0x20381400`–`0x20381E38` | 约 `0x100` 附近的网格（地址表 `0x1068B598`，22×0x40 + 14×0x44） | 镜头暗角补偿 |

没有发现大小像 3D 网格（9³×3、17³×3 等）的写入区域。“用途”一列只按数值形状推断，尚未绑定寄存器语义。

### Picture Control 对比：未得到结论

探针 `probe_pc_tables.py` 在 StartLV 前调用 `0x101F5210(0x526, 0x80B)`，读回值为 11：设置只保留了低字节，实际写入的是 11 号，不是假设中的创意优化校准 `0x80B`。与默认值 0 的运行相比，所有表内容完全相同；只有 `0x20380310`–`0x2038031C` 的 DMA 缓冲地址不同，另有一处一字的运行边界偏移。

可能的原因：取值 11 对应的 Picture Control 与默认的色彩参数相同；设置要经过另一次刷新才会重新编译；或者辅助启动路径用的是固定配置。尚无法区分。**目前不能断定哪些表由 Picture Control 控制。**

## 第三轮：每帧参数结构与 Picture Control 取值

### 参数应用函数是实时 LUT 的接入点

`0x100C93B6(ctx=r4, params=r5)` 按字段把参数结构交给 `0x1011B812`–`0x1011E5CE` 中的寄存器写入函数。每个字段是指向模块参数块的指针，为空则跳过该模块，因此这是一个按模块增量更新的接口。逐字段静态解析调用链和写入函数引用的 MMIO 页，得到色彩相关部分：

| 参数字段 | 写入函数 | 表 RAM |
| --- | --- | --- |
| `+0x40`、`+0x44` | `0x100C92A0` → `0x1011D800` | `0x20382400`–`0x20382A94` |
| `+0x48` | `0x1011D828` | `0x20382890`、`0x20382A94` |
| `+0x5C` | `0x100CA0E2` → `0x1011D8E8` ×4 | 6 份 gamma：`0x20383900`、`3AA0`、`3C40`、`3DE0`、`3F80`、`4120` |
| `+0x60` | `0x1011DCC8` | `0x20384D14`、`0x20384E1C` |
| `+0x64` | `0x100CA080` → `0x1011DAD6` ×5 | 65 点表 `0x20384A74`、`0x20384C8C` |
| `+0x70`、`+0x74` | `0x1011DD60`、`0x1011DD72` | `0x20384FA4` |
| `+0x78` | `0x1011DD96` | 257 点曲线 `0x20385134`、`533C`、`5544`、`574C`，以及 `0x20385954` |
| `+0x84` | `0x1011DE3E` | 65 点增益曲线 `0x20385AE4` |
| `+0x88` | `0x1011DA40` | `0x203842C0` |
| `+0x8C`–`+0x9C` | `0x1011DA84` | `0x203844C8`、`45D0`、`46D8`、`47E0`、`48E8` |
| `+0xA8`–`+0xB0` | `0x1011E2BC`/`2C6`/`2D8` | 36 段色相表 `0x20381F90` 起 |
| `+0xB4`、`+0xB8` | `0x1011E3F4`、`0x1011E45A` | `0x20382080` |
| `+0xBC` | `0x1011E47C` | `0x20385C80`、`0x20385D80` |
| `+0xC0` | `0x1011E4C8` | `0x20381F48` |

意义：实时 LUT 不需要自写寄存器。只要在 `0x100C93B6` 之前，把相应字段指向由 `.cube` 拟合出的曲线和色相表，原厂写入函数就会在下一帧上传。各表的具体语义仍按数值形状推断，需要逐个寄存器确认。

动态断点在 `0x1011E734` 只捕获到 5 次小表上传（返回地址 `0x100C9587`/`0x100C9593`/`0x100C95FF`），gamma 等大表的上传没有触发；第二轮 `0x1019F5CE` 的断点也一样没有命中。原因未查明，表内容因此改从 MMIO 写记录提取。

### Picture Control 取值与对比

`0x526` 的运行时取值表（`0xC18AD19C` → `0xC24FFAE4`，容量 37）共 28 项，取值 0–27：推测为 8 个标准项加 20 个创意项，当前没有自定义项。因此设置值是索引，不是 `0x80x` 编号；上一轮写入的 `0x80B` 被截成 11。

在 StartLV 之前写入 4（按顺序推测为单色），读回为 4，但所有表和寄存器的最后取值都与默认值 0 的运行完全相同。推测取景参数在这之前已经算好，而 `0x101F5210` 只改存储、不触发重新计算。

改为在 `prepare_capture_boot_fixture` 刚结束时写入 4（与夹具写 `0x41C` 等设置的时机相同，读回为 4），结果仍然一样：所有表和寄存器的最后取值与默认运行相同，差异只有 DMA 缓冲地址 `0x20380310`–`0x2038031C`，以及两处连续写入段的切分位置。

结论：在 QEMU 辅助启动路径中，单改 `0x526` 的存储值不会改变取景 ISP 表。可能的原因包括：Picture Control 要经过原厂设置服务的变更通知或 `PICCON` 服务的重新编译才会下发；或者辅助启动的取景参数来自固定的默认数据。这一点只说明“改存储值”这条路无效，不代表取景表与 Picture Control 无关。

## 第四轮：取景色彩表的生产者

### 调用链

1. `0x100C93B6` 的直接调用者是 `0x100AA6B2`/`0x100AA6BE`（实例 1 和 2）；另有 ISP 驱动任务内的消息处理函数 `0x100C9A14`/`0x100C9B20`（消息码 `0x42180806` 加偏移，请求 `+0x14` 为参数结构）。
2. `0x100AA6B2` 之前先调用 `0x100AAD52(sb, params=obj+0x34, buf=obj+0x108)`，再对 `obj+0x108` 的 0x7E8 字节做缓存 clean+invalidate。
3. `0x100AAD52` 依次调用 `0x100AA084(params, buf)`（把各字段指针绑定到缓冲内）和 `0x100A94FC(sb, params)`。
4. `0x100A94FC` 不计算表，只把参数字段指向三个源对象：`sb+0x35C`、`sb+0x360`、`sb+0x364`。色彩表都在 **表存储 `sb+0x360`** 里，每张表有固定偏移和一个有效标志（`+0x39A8` 起的字节）。从中解析出的部分对应关系：

| 参数字段 | 表存储偏移（有效标志） |
| --- | --- |
| `+0x5C`（gamma） | `+0x798`（`+0x39E9`）、`+0xC6C`、`+0xE08`、`+0xFA4` |
| `+0x64`（65 点表） | `+0x3188`、`+0x3314`、`+0x3398`、`+0x341C` |
| `+0x60` | `+0x34A0` |
| `+0x70`、`+0x74` | `+0x3080`、`+0x1858` |
| `+0x40`、`+0x44`、`+0x48` | `+0x25C0`/`+0x2704`、`+0x2848`/`+0x294C`、`+0x2A50`/`+0x2C54` |

`+0x78`、`+0x88`、`+0xA8` 等字段的寄存器写法不同，脚本没有解析出来，尚未列入。

### 取景表是 ROM 常量，按 Picture Control 编号选择

QEMU 中取景 ISP 实际写入的表，在 ROM 里都能找到完全相同的副本，位于约 `0x116B8000`–`0x11800000` 的调校数据区：gamma 在 `0x116BA4D6`，257 点曲线在 `0x116BE2B0`、`0x116C8AA0` 等，65 点增益曲线在 `0x116B8A08`，36 段色相表在 `0x1172D460` 起。同一种表有多份变体并排存放，例如 257 点曲线有 `0x116C869C`、`0x116C889E`、…、`0x116C92A8`。唯一没找到的是 `0x20385C00` 的 512 字节表。

选择函数 **`0x101B9ABC(index, out_a, out_b, out_c)`**：

- `index` 上限钳到 `0x1C`，共 29 行。
- 从 `0x117FFF3C + index×0x20` 复制 8 个表指针到 `out_a`。
- `index < 9`：再从 `0x118002DC + index×0x54` 复制 21 个表指针到 `out_b`，`*out_c = 0`。
- `index ≥ 9`：`*out_c = 0x118005D0[index − 9]`（钳到 0…19），再处理 `out_b`。

即 9 个标准 Picture Control（0–8）加 20 个创意项（9–28），每项对应一组 ROM 表指针。这就是 Picture Control 影响取景色彩的方式：**编号选择预先调好的表**，不是在机内计算。

调用者有两个，可能分别对应两条管线：

- `0x101B9E48`：编号取自 `[ctx+0x144]` 的第 3 字节。若 `[ctx[0]]+0x7B` 非零，就不走选择函数，改走 `0x101B9B26`。推测这是自定义 Picture Control（带曲线）的计算路径，尚未验证。
- `0x101C0480`：编号取自 `[ctx+0x28]+0x23`。这正是前面写表存储 `+0x798`、`+0xC6C` 的 `0x101C0xxx` 代码。

这也解释了 QEMU 对比为什么无效：改 `0x526` 的存储值，不会更新 `ctx` 里已经缓存的编号。

### 对实时 LUT 的意义

最直接的接入方式：在 `0x101B9ABC` 返回后（或在两个调用点），当某个 Picture Control 槽位被选为“LUT”时，把 `out_a`/`out_b`/`out_c` 中的指针换成指向 RAM 中拟合表的指针。表格式与原厂 ROM 表相同（gamma、257 点曲线、65 点曲线、36 段色相），只需换掉表内容。这样取景、拍照、视频都由原厂代码按同一组表处理，CPU 开销为零。

还需确认三件事：

1. 每张表的语义和数值格式（输入/输出位数、色相表 36 字节的含义），以便从 `.cube` 拟合。
2. 拍照（`IMPIIP`）是否也经同一个选择函数，或者另有一组表。
3. `0x101B9B26` 自定义路径计算了哪些表，能否借它直接写入拟合结果。

## 第五轮：Picture Control 表组的格式

### 表组布局

每个 Picture Control 编号在 ROM 中有一段连续的表组，A 组（8 个指针，`0x117FFF3C`）和 B 组（21 个指针，`0x118002DC`）都指向这段数据内部。各项长度按相邻指针的间距计算（编号 0）。“各编号”一列按 9 个标准编号逐项比较内容哈希：“同”表示 9 个都相同。“编号 8”一列是推测为单色那一组的取值。

| 槽位 | 长度 | 元素 | 编号 0 示例 | 编号 8 | 各编号 | 取景写入位置 |
| --- | --- | --- | --- | --- | --- | --- |
| A0 | 0xC | 6×u16 | 128, 256, 256, 192, 3540, 3600 | 0, 0, 0, 0, 3600, 3900 | 不同 | 未直接写入 |
| A1 | 0x42 | 33×u16 | 110, 174, 230, 250, 256… | 全 256 | 不同 | 未直接写入 |
| A2 | 0x180 | 32×6×s16 | (252, 22, −22, 252, 12, 0), (248, 16, −16, 248, 12, 2)… | 每组 (256, 0, 0, 256, 0, 0) | 不同 | 未直接写入 |

### 格式推断

- **按色相分段的色度矩阵（A2）**：32 个色相段，每段 6 个 s16。前 4 个形如 `(a, b, −b, a)`，符合 Q8 的 2×2 旋转加缩放矩阵（作用于 Cb/Cr），后 2 个推测为偏移或权重。单色时每段都是单位阵，色度归零应由别的槽位完成（例如 A0 前 4 项变为 0）。
- **色相段参数（B2、B15）**：B2 为 32 段 × 8 个 s16，单色全 0；B15 为 4 × 32，单色时前 32 项 0、后段 1024（Q10 的 1.0）。
- **亮度索引增益**：A1（33 点）、A3（2×33）、B1（8×33）为 Q8 增益曲线，单色全为 256（1.0）；A4 为 25 点 Q10 增益。
- **257 点曲线**：A6、A7（各 3 条）和 B16–B20（各 2 条）。A6 首条与 B17 相同，并被直接写入取景 ISP，应为色调曲线；B19 全为 4096，像中性增益。

由此看，取景色彩引擎大致是：色调曲线 + 按 32 个色相段的色度矩阵与参数 + 按亮度的增益曲线。这比“矩阵 + 1D 曲线”多出一个色相维度，能表达大部分随色相变化的风格化调色，但仍不是完整的 3D LUT：没有发现按 (R, G, B) 网格索引的表。

### 尚未打通的部分

- A0–A5、A7、B2、B16、B20 在 QEMU 取景运行中没有被原样写入，可能先换算成寄存器值，也可能只用于拍照管线（`IMPIIP`）。
- `0x20381F90` 的 8×36 字节色相表来自 ROM `0x1172D460`，不在任何 Picture Control 表组里，暂不清楚由什么决定。
- 色相段的角度起点与方向、色度矩阵后 2 项的含义、各曲线的输入输出位数，都需要逐个找到消费代码确认。

## 下一步

0. **找到 Picture Control 进入取景参数的路径。** 已完成，见第四轮。 改存储值无效，下一步有两条路：一是走原厂菜单或设置服务的正式变更入口（带通知）来切换 Picture Control；二是从参数应用函数 `0x100C93B6` 往回追 `r5` 结构的生产者，看 `+0x5C`、`+0x78`、`+0xA8` 等字段指向的缓冲是谁填的、读了哪些设置。后者不依赖 QEMU 能否模拟设置变更，更稳。
1. **追 `LVIIP` 的色彩阶段配置。** 从任务入口找到它接收的参数块，确认有哪些阶段：矩阵、每通道或亮度曲线、色相/饱和度表，以及是否有 3D 表。这决定实时 LUT 能做到多精确。
2. **追 Picture Control 的编译器。** 从 `PICCON`、`0x900` 设置块追到写入 `LVIIP`/`IMPTM` 参数的代码，确认 NP3 曲线的点数和下发位置，以及创意 Picture Control 如何表达色相偏移。
3. 根据第 1、2 步选择方案：
   - **管线中有每通道曲线或色相表**：固件钩子在 Picture Control 编译后替换这些表，填入由 `.cube` 拟合出的参数。取景、照片、视频一致，CPU 开销为零。
   - **只有一条曲线**：先做电脑端 `.cube → NP3` 转换器（以“平面”为基准，拟合曲线和饱和度/色相参数，并报告 ΔE）。不改固件就能上机。
4. 精确预览作为补充：冻结一帧显示缓冲，用 CPU 3D LUT 处理后静态叠加。

## 复现

静态分析使用临时脚本读取 `build/research/stock-eg.bi`（原厂 EG 模块，基址 `0x10020000`，初始化数据映射同 `z30_extensions.platform.z30_120.SCATTER`），用 Capstone 反汇编。动态数据来自 z30-qemu 的辅助 StartLV（`functional_raw=True`，合成渐变 Bayer 输入），在 WSL 内运行，表内容从 `.local/<prefix>/devices.log` 的 MMIO 写记录提取。探针脚本（`probe_lut_unit.py`、`probe_pc_tables.py`）目前在会话临时目录，尚未整理为 `tools/` 下的正式工具。QEMU 结果只说明原厂配置代码写了什么，不代表真实传感器、ISP 输出或机身行为。
