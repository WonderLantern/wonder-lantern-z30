## 组成

| 部分 | 内容 |
| --- | --- |
| 常驻 EG | 原厂；扩展的 CJK 字体（开机就读，必须常驻，带常用字集，见下文）；加载器；IMU 任务触发点 `0x1021C360`（原厂调用和分支保持不变）；固件版本页上的项目名和版权（见下文） |
| `Z30/WL.PATCH` | 所选功能的 tail（在 `0x20000000` 链接）、tail 重定位、改动（代码区或主 RAM）、加载完成时要调用的函数 |

- 卡文件头带有常驻 id，只能配对应的常驻 EG 使用。
- 常驻 EG 的报告（`EG209020.json`）记录加载器的能力 `capabilities`：格式版本、支持的段类型、可写的代码区和 RAM 范围、初始化接口版本、常驻字体补上的全部字。
- 以后加功能或改功能只换卡文件。只有新功能用到了常驻加载器不具备的能力，或者用到常驻字体里没有的字时，才需要重刷 EG。

## 固件版本页上的项目名和版权

常驻 EG 在 Setup → Firmware version 页的版本行和“完成”之间显示两行（`features/card/firmware_banner.py`，无卡也显示）：

```
Wonder Lantern Z30
(c) 2026 CaCl2 (GitHub: RealCaCl2)
```

- 原厂页面构建函数 `0x104D05FA` 给每个存在的固件组件（C、LF……）分配一对原厂文字控件（`0xC94/0xC95` 起，最多 5 对），第 i 对用文字槽 2i、2i+1，再按组件数从布局表取位置。
- 钩子在布局入口 `0x104D075C`（r4 = 组件数），在原厂布局之前把最后一对控件 `0xC9C/0xC9D`（只有第 5 个组件才会用，文字槽 8/9）设成样式 47（字体 0x16、24 号、居中），放在 y 258–318，然后原样重放被替换的 `cmp/blt/ldr/mov` 回到原厂流程。
- 组件数 ≤3 时版本行最低到 y 256，“完成”从 y 322 开始，不重叠；实机插卡且有升级包时“完成”下面还有“版本升级”“删除固件更新文件”，所以不能放在“完成”下面。组件数 ≥4 时不显示。
- 另一条 `0x111` 配置路径（11 组件布局）不经过钩子，保持原厂。
- 常驻 tail 开头另有一段 ASCII（项目名、版权、MIT License），十六进制查看 EG 即可看到。
- QEMU（`output/card-banner-v1`）：简、繁、英三种语言都打开原厂固件版本页 `0xC1839680` 并显示两行；把组件表改成 2、3、4 个组件模拟镜头等：2、3 个时不重叠，4 个时不显示。

## 常驻字体与常用字集

为了加字时不用重刷，常驻 EG 的字体 2（简体）补全 GB2312 一级字（3755 个），字体 0（繁体）补全 Big5 常用字（5401 个）。原厂各只有约 720 个汉字。

- 新补字形：简体 3064 个，繁体 4705 个，平均约 350 字节。扩展后字体 2 约 1.31 MB，字体 0 约 2.15 MB。常驻 EG 约 37.4 MB，低于 EG bank 的 `0x2940000`。
- 区间内的偏移是 16 位，所以新字形按 64 KiB 分成多个索引区间（`platform/fonts.py` `extend_font`）。
- 普通整包构建仍然只补标签用到的字，产物与以前逐字节相同；只有 `card.build_resident` 用 `common=True`。
- 字形由 `tools/build_cjk_glyphs.py` 从 Noto Sans CJK 生成，存在 `platform/z30_120_extra_glyphs.json`。
- 卡构建会检查所有中文标签用到的字是否都在已刷常驻 EG 的字体里（原厂字加报告中 `capabilities.glyphs`）。缺字时报错，提示重刷。

## 构建

```powershell
python tools/build_card.py --source Z_30_0120.bin --output output/card
```

- 用 `--preset` 选功能，例如 `--preset focal-length battery-percent`。
- 只更新卡文件时加 `--patch-only`，输出目录指向放着已刷常驻 EG（`EG209020.BIN` 和 `EG209020.json`）的那个目录，并先移走旧的 `Z30/WL.PATCH`。
- `--patch-only` 按**已刷的常驻 EG**构建，不会重新计算常驻 EG。所以工具升级后，只要卡文件没用到旧加载器不具备的能力，仍能给旧常驻 EG 出卡文件。用到了（例如需要加载完成入口，或者缺字），工具会说明原因并要求重刷。
- 常驻报告里没有 `capabilities` 的第 1 版常驻 EG，会被提示加载器太旧。
- `--menu-tab`：扩展菜单放在菜单左侧第 8 个标签，不再占设定菜单的一行（[说明](menu-framework.md#菜单左侧第-8-个标签构建选项-menu_tab2026-11-24)）。2026-11-25 已上机，默认仍关闭；完整检查见下面"实机检查"第 6 步。
- 卡文件默认带[取景就绪提示](ready-banner.md)（加载成功后照片取景上方显示约 2 秒），`--no-banner` 去掉；`--banner-debug` 在状态页"版本"一行显示提示的诊断读数。
- `--build-tag` 指定状态页"版本"一行的文字，默认是"月-日 git 短哈希"。

## 卡文件格式（第 2 版）

文件头 24 字节：`WLCP`、格式 2、常驻 id、链接基址、主体长度、主体 CRC32。主体由若干段组成，每段是"类型 u16、标志 u16、长度 u32、内容"，长度按 4 字节对齐。

| 类型 | 内容 |
| --- | --- |
| 1 TAIL | 功能代码和数据，必须是第一段 |
| 2 RELOCS | tail 重定位：每个字的高 4 位是类型（0 = ABS32，1 = MOVT），低 28 位是偏移 |
| 3 EDITS | 改动条数，然后逐条：运行时地址、长度、重定位条数、预期字节、新字节、重定位 |
| 4 INIT | 加载完成后要调用的函数，存的是在 tail 里的偏移 |

- 标志第 0 位是 REQUIRED。加载器遇到不认识的必需段，会拒绝整份文件（`S=0D`）；不认识的可选段直接跳过。以后加新能力时可以按这个规则扩展。
- 改动按运行时地址区分写法：
  - `0x10020000..0x106FFFFF` 的代码经 DRAM 别名写入，并同步缓存；
  - `0xC1800000..0xC79FFFFF` 的主 RAM（scatter 数据、bss、堆）直接写入。
  - 不在这两个范围内的改动，整份文件都会被拒绝。

## 功能代码可用的接口

- `plan.ram_edit(address, replacement, expected, name)`：只用于卡构建，改主 RAM 中的一段数据，例如 bss 里的全局变量。`expected` 是运行时那里应有的值，加载器先核对，不符就不加载。只有运行时才知道的值，放到加载完成函数里处理。
- `plan.on_load(function)`：只用于卡构建，登记一个 tail 里的 Thumb 函数。加载器写完所有改动后，在 IMU 任务里调用一次 `f(info, tail_base, tail_size)`，返回 1 表示成功，否则日志为 `S=0E`（改动已写入）。
  - `info` 是常驻加载器的服务表，依次为：接口版本 1、表长度 24、跨核缓存同步函数、状态字地址、内存池分配、内存池释放。
  - 这些函数地址也可以直接写原厂地址；服务表主要提供常驻加载器自己的函数。
- 普通整包构建里这两个接口会直接报错。功能如果要同时支持整包构建，需要另写一条路径。

## 加载过程

1. IMU 任务约每 50 ms 一个 tick。开机约 3 秒后开始尝试打开 `A:\Z30\WL.PATCH`，每 0.5 秒一次，约 30 秒后放弃。
2. 找到文件后：
   - 读头部，检查魔数、格式、常驻 id 和大小；
   - 从原厂内存池申请"文件主体 + 64 KiB + 8"，把主体读到让 tail 段内容正好落在 64 KiB 边界的位置，确认读到文件末尾，然后关闭文件；
   - 检查 CRC32，逐段检查结构，检查重定位范围、加载完成函数的偏移，以及每条改动的目标范围和预期字节。
3. 全部通过后：
   - 重定位 tail，对它做双核缓存同步；
   - 逐条重定位并写入改动，每条代码改动都同步缓存；
   - 依次调用加载完成函数。
4. 写入之前任何一步失败，都会释放内存，不做任何改动。

## 卡文件构建时如何处理不可写区

EG 的 `0x10700000` 之后不可写，三处改动改成"RAM 副本 + 改指针"。这些处理只在卡构建里生效，普通整包构建保持字节不变：

- **菜单回调记录**（声音入口、照片菜单、视频菜单）：复制 5 个字，改菜单对象 `+16` 处的指针（对象在 scatter RAM 里）。
- **码率表** `0x10713154`：放一份改好的副本，改可写区里的字面量 `0x10355798`。
- **Wi‑Fi 国家表** `0x114A37BC`：放一份改好的副本，改字面量 `0x101F51EC`。

`0x10700000` 之后的原厂代码仍然不能直接挂钩，约占原厂函数的三分之一。需要时可以从低区的调用方或 RAM 里的函数指针绕过去；要彻底解决需要改页表（见计划中的第四项）。

## 状态与日志

只要找到了文件，就会写 `Z30/WL.LOG`，内容一行，形如 `WL.PATCH S=01 B=D0010000 T=0001CDE0 E=00000078`：

- **S**：结果代码，含义见下表；
- **B**：tail 的基址；
- **T**：tail 大小；
- **E**：改动条数（含 RAM 改动）。

| S | 含义 |
| --- | --- |
| 01 | 加载成功 |
| 03 | 读文件失败 |
| 04 | 文件格式或大小不对 |
| 05 | 卡文件不是给这个常驻固件构建的 |
| 06 | 内存不足 |
| 07 | CRC 不对（文件损坏） |
| 08 | 结构错误（段、重定位、改动范围或加载完成函数偏移不对） |
| 09 | 相机内存与补丁预期不符（没有写入） |
| 0A | 关闭文件失败 |
| 0B | 缓存同步失败（没有写入） |
| 0C | 写入后有代码区缓存同步失败，需重启 |
| 0D | 卡文件含有这个常驻加载器不认识的必需段，需要更新常驻 EG（没有写入） |
| 0E | 某个加载完成函数没有返回 1（改动已写入） |

没有文件就不写日志。RAM 状态字是 `0xC1832D30`（菜单记录 0 的 `+0x0C`）。

## 实机检查

只换卡文件时，出问题拔卡或换文件即可恢复，不需要检查固件升级。刷新的常驻 EG 时仍要做第 1 步：没有卡时相机启动的就是它，只能通过固件版本页把它换掉。

1. 刷常驻 EG，**不放卡文件**：确认 Setup → Firmware version 能正常进入、升级流程正常，版本行下方显示项目名和版权两行（装上镜头后 LF 行也不被遮挡）；菜单、拍照、录像和原厂一致；卡上没有 `WL.LOG`。
2. 放入 `Z30/WL.PATCH` 并重启：约 3 秒后功能应出现；`WL.LOG` 显示 `S=01`。逐项试用：扩展菜单、声音、画幅、同屏、码率、斑马纹、日期戳、竖拍 UI、陀螺仪、3D 跟踪、对焦框颜色、焦距显示、Wi‑Fi、NEF 菜单、MTP。
3. 加载后再确认 Setup → Firmware version 正常。
4. 放一个损坏的文件（改一个字节）：`WL.LOG` 显示 `S=07`，相机保持原厂。
5. 拔卡重启：恢复原厂。
6. 第 8 个标签（`--menu-tab` 构建；最早用 `output/card-v3-menutab`，2026-11-25 在 `output/card-banner-v1-categories` 上确认了进入根页和分类页，下面其余各项仍要逐条看）：
   - 开机等 3 秒后按 MENU：左侧有 8 个标签，最下面是灯笼图标，"?"帮助图标仍在；设定菜单里没有"自定义菜单"一行；
   - 开机后立刻按 MENU（加载前）：应是原厂 7 个标签；关掉菜单、等几秒再打开，应出现第 8 个标签；
   - 焦点在灯笼标签上时按 OK 或右键：进入"自定义菜单"，焦点在第一行，左键返回标签栏（第一次上机 OK 进了设定菜单、第二次右键进不去，已修正）；
   - 灯笼标签被选中时，标签栏右边的竖色条是青色，和图标的强调色一致（原来是浅灰色）；其他标签的色条不变；
   - 点灯笼标签：右侧是"自定义菜单"，标题居中、没有返回箭头；进各功能页再返回，右上角没有残留的框；上下键在 8 个标签间循环；
   - **停在第 8 个标签上退出菜单**，再打开：应回到设定标签；停在第 8 个标签上直接关机，再开机打开菜单：同样；
   - 然后**拔卡**开机打开菜单：原厂 7 个标签，显示正常，固件版本页能进入。

## 已知风险

- 修改代码时另一个核可能恰好在执行被改的函数。加载放在开机约 3 秒、通常空闲的时候，但无法完全排除。
- 只在 IMU 任务运行时才会加载。如果某些开机模式下 IMU 任务不运行，功能就不会出现，日志也不会写。
- 菜单之类的数据如果在加载前已被原厂缓存，改动可能要重新进入页面才生效。
- 开机约 3 秒内功能不可用。
- 加载完成函数在 IMU 任务里运行，应尽快返回；它返回失败时改动已经写入，不会回滚。
