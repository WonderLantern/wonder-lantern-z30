# 对焦追踪交接研究（af_log，研究用，未进 `full`）

2026-11-13 开始。目标：自动区域 AF 下按 OK 开始追踪后，如果人物或动物检测在追踪框附近发现主体，就把追踪交给检测到的主体。原厂不会这样做（2026-11-13 实机确认：追踪框不会自己跳到脸上）。

## 第 1 份日志（2026-11-13，`AF000084.BIN`，1169 个 tick、982 次变化）

- `+0xA8` 的人脸框**跟随实时取景更新**（约 10–20 Hz）。X、Y、宽、高是粗网格坐标（X 约 22–48、Y 约 11–26、宽高 3–25）。第一个值在某些时段不为 0（如 6.96–8.56 s、23.2–27.4 s 时为 112–485），同时 `+0x130` 为 1、`+0x12C` 的 bit 24 置位，推测是"人脸被对焦采用"（半按），有待确认。
- `+0x90` 的对焦框整段都是 0。
- `+0x108`/`+0x10C`/`+0x110` 在 31.9 s 之后交替翻转，可能对应追踪状态；因为没有各段操作的时间，现在还不能确定。
- 追踪框的位置**不在**这块记录里。
- 写人脸框的是 `0x101944B0`，调用点在 `0x10071D36`。它先把一个 0xF0 字节的检测结果复制到 `0xC237E2E8`，再把人脸 X/Y（int16）和宽/高（int16）写进记录的 `+0xAC..+0xB8`。第 2 份日志会把这 0xF0 字节也记下来。

## 第 1 步：只读记录（当前）

- 固件：`python3 tools/build_af_log.py --source Z_30_0120.bin --output OUTDIR`，生成 `OUTDIR/EG209020.BIN` 和 `OUTDIR/Z30/CORE.ZMOD`。EG 是 `full` 去掉 `gyro-evr`（它占用 IMU 钩子），加上 SD 模块宿主和 IMU 钩子。
- 解析：`python3 research/af/parse_aflog.py AFnnnnnn.BIN --words`，列出对焦框、人脸框的每次变化，以及哪些地址的字变过（第 1、2 版都能读）。
- 验证：

### 第 2 份日志的上机步骤（请照时间做，并告诉我实际的秒数）

## 第 2 份日志（2026-11-13，`AF000118.BIN`，1854 个 tick；按步骤顺序做，没有计时）

| 地址 | 含义（按步骤顺序对照） |
| --- | --- |
| `0xC237E3E4` | 检测到的主体数量（0–5）：第 1 步 0，第 2 步 1，第 3 步 2–5 |
| `0xC237E2E8` 起 0xF0 字节 | 每个主体 4 个值，存放方式是 4 个字段 × 15 个槽位，每个字段内按"5 个一组 × 3 组"排列；第 n 个主体在每组的第 1 格。4 个值同比例变大变小，脸靠近时变到 2000–4000：更像大小或分数，**不是位置** |
| `0xC237E2C0` | 人脸状态：257（0x101）检测到并被对焦采用，1 检测到但没被采用，4 没有人脸 |
| `0xC237F688` | 只在按 OK 追踪时为 1（第 4、5 步）：**正在追踪** |
| `0xC237F680` | 追踪或半按对焦时为 1（第 4、5、6 步）：AF 正在工作 |
| `0xC237F684` | 第 4 步里和 `F688` 交替：推测是追踪框已显示、还没开始追踪 |

第 5 步（追踪中让人脸靠近）里，`F688`=1、主体数量为 2，但人脸状态是 1 而不是 257：**原厂检测到了人脸，但因为在追踪而不采用**。这就是交接逻辑的切入点，数据都已经能读到。

追踪框的位置不在这两段内存里。追踪期间一直在变的只有 `0xC237F584`/`0xC237F588`，更像对焦位置。

## 第 3 步：扫描"只在追踪时才变的字"（当前）

- 模块：`modules/af_scan/af_scan.c`（1.8 KB）。它扫描 `0xC2300000` 起 1 MB，每个 IMU tick（50 ms）扫 64 KB，16 个 tick 扫完一轮。每个字和上一轮比较，变了就按当时的 `0xC237F688` 记到"追踪"或"非追踪"；追踪时还记下最小值和最大值。申请约 4 MB 内存，结果最后一次写成 `Z30/SCnnnnnn.BIN`（约 3 MB）。只读。
- 构建：`python3 tools/build_af_log.py --source Z_30_0120.bin --output OUTDIR --module scan`（研究 EG 和第 1、2 步相同，只换 `CORE.ZMOD`）。
- 解析：`python3 research/af/parse_afscan.py SCnnnnnn.BIN`，列出追踪时常变、非追踪时几乎不变的字，按相邻地址分组，并给出追踪时的取值范围。
- 验证：Unicorn `research/af/emulate_afscan.py`（`tests/test_af_log.py`）。

## 第 3 份日志（2026-11-13，`AF000299.BIN`，按步骤做）：追踪框找到了

| 地址 | 含义 |
| --- | --- |
| `0xC237D59C` 高 16 位 | 追踪框左边 X（传感器尺度，约 254–5314） |
| `0xC237D5A0` 高 16 位 | 追踪框右边 X（= 左边 + 552） |
| `0xC237D5A0` 低 16 位 | 追踪框上边 Y（约 200–2720） |
| 环形队列每份的第 3 个字 | 追踪框下边 Y（= 上边 + 552） |
| `0xC23AA028` | 同一个框的粗网格坐标：低 16 位是 X，高 16 位是 Y |

和操作对照：向左转相机，框右移，X 从 2508 增加到 4762；向上抬相机，框下移，Y 从 1580 增加到 2720。

人脸框（`0xC237F578+0xAC`，X/Y/宽/高，粗网格）换算到追踪框的单位，约为 1 格 = 106。人脸靠近追踪框的两个时刻（43.8 s、45.6 s）前后一致。此时主体数量 = 1，人脸状态 = 1（检测到但没被采用）。

结束追踪：原厂按键入口 `0x103CE96E(事件号)`，OK 键为 `0x27E`（z30-qemu 的按键表：上 0x253、下 0x254、左 0x257、右 0x258、返回 0x255）。QEMU 工具是在 UI 任务的消息循环里（`0x100531BC`）调用它的，所以不能从 IMU 任务直接调用。需要找到按键事件进入 UI 任务的消息队列，从别的任务往这个队列发一条 OK 事件。

## 第 4 步：交接验证模块（af_handover）

结束追踪不找追踪器内部的函数，而是"按一下 OK"：调用原厂按键函数 `0x103CE96E(0x27E)`。

真实按键的整条路径都在 UI 任务里：输入状态（0x18C 字节的按键位图）由 `0x102F0D14` 写进 16 格的输入环形缓冲区（`0xC2008EA0`，每格 0x190 字节），`0x102F1AB6` 读出按键码，`0x1045933E` 把它转成事件，最后交给 `0x103CE96E`。原厂没有"从别的任务投递按键"的入口。QEMU 的全部菜单检查都是在开机任务的空闲循环（`0x100531BC`）里直接调用 `0x103CE96E` 发按键，也就是从非 UI 任务调用，所以模块用同样的调用方式。

- 模块：`modules/af_handover/af_handover.c`（1.9 KB）。每个 IMU tick（50 ms）检查以下条件，连续 5 次（约 0.25 秒）都成立就按一次 OK：
  - 正在追踪（`F688`=1）；
  - 主体数量为 1–5；
  - 人脸状态**正好是 1**（检测到但没被采用；257 = 0x101 表示已被采用，不能只看低字节，Unicorn 测试抓到过这个错误）；
  - 人脸点（网格 x、y × 106）到追踪框中心的水平、竖直距离都不超过"框边长 × 1.5 + 半个脸宽"。
- 每次追踪最多按一次。追踪结束满 1 秒后，才允许下一次。
- 追踪期间每个 tick 都记一条（时间、主体数、人脸状态、追踪框、人脸框、偏移、是否按了 OK），Run 时写成 `Z30/HOnnnnnn.BIN`。解析用 `research/af/parse_afhandover.py`。
- 用第 3 份日志离线回放这套规则：只在 45.78 s 按一次（人脸靠近追踪框的那一段），其他追踪时段都不触发。
- Unicorn（`research/af/emulate_afhandover.py`，`tests/test_af_log.py`）：人脸远离不按；靠近 4 次不按，5 次按一次；同一次追踪不重复按；追踪结束不满 1 秒不重新允许，满 1 秒后再靠近会再按；人脸已被采用（0x101）不按；没在追踪不按。
- 构建：`python3 tools/build_af_log.py --source Z_30_0120.bin --output OUTDIR --module handover`（研究 EG 不变）。
- 风险：从 IMU 任务调用 UI 的按键函数，最坏情况是相机卡住，需要拔电池重启；不会变砖。模块要手动加载，开机不会运行，固件版本页始终能进。

### 第 1 次上机（`HO000093.BIN`）：没有触发，规则已改

- 现象：追踪照常进行，没有变成人脸框。
- 原因一：追踪期间人脸状态大多是 **0x101**（追踪框已经跟着这个人或这张脸），而第一版要求状态正好是 1。
- 原因二：检测结果按 tick 交替出现和消失（主体数 1、0、1、0……），而第一版要求"连续 5 次"，遇到 0 就清零，永远凑不满。
- 第二版规则：
  - 正在追踪时，人脸状态低字节为 1 或 2 就算"检测到人脸"（0x101 也算）；
  - 检测到的人脸在追踪框附近就加 1 分；检测到人脸但离得远，分数立即清零；没检测到时分数不变，连续 5 次都没检测到才清零；
  - 累计 5 分就按 OK。
  - 日志里人脸状态改为保留 0x100 位（bit 7），文件头改为 `AFHAND2`。
- 回放（`research/af/replay_handover.py`，规则和 C 代码一一对应）：`HO000093` 在 9.34 s 触发，人脸离得远的第二段不触发；`AF000299` 仍只在 45.78 s 触发。
- Unicorn 新增两个场景：检测时有时无（状态 0x101）会在累计 5 分时触发；连续 5 次没检测到会清零。

### 第 2 次上机（`HO000087.BIN`）：按了 OK，但追踪没结束

- 模块在 13.23 s、22.53 s 各按了一次（规则和回放一致），但追踪标志一直是 1，追踪框也一直在动。
- 原因：在拍摄取景画面里，`0x1042ADE4` 不把按键转成界面事件，拍摄程序直接读原始输入状态。`0x103CE96E` 只对菜单和对话框这类界面页面有效，QEMU 也只验证过菜单。
- 第 3 版改为合成**原始按键**：`0x102F199A(按下[4], 保持[4], 0, 0, 0)`（原厂调用点 `0x1039E1D4`、`0x1046497E`）。它把"按下"和"松开"两份输入状态放进真实按键所走的输入环形缓冲区。
  - 按键码 ↔ 位的对照表在 `0x1073BD68`（每项：掩码，按键码）。第 0–22 项对应第 1 个按键字，第 23–41 项对应第 2 个按键字。OK = 按键码 0x1B = 第 29 项 = **第 2 个按键字的掩码 0x1**（上 4、下 5、左 6、右 8、返回 3 都在第 1 个字）。
  - 合成函数里，按下位图 = 新按下的键，保持位图 = 一直按住的键；它会先放一份"按下"、再放一份"松开"。
  - 原厂调用前会先调 `0x102F14DE(0)`：那是 UI 任务读掉并丢弃待处理的输入，不能从 IMU 任务调用，所以模块不调。
  - 风险：合成函数会写一份全局的临时输入状态；如果 UI 任务恰好同时在处理真实按键，可能会冲突。最坏情况是多一次或少一次按键，或者卡住需要拔电池。
- 日志：按下 OK 那一条的 `tracking` 字段记录为 0x80 | 合成函数返回值；文件头改为 `AFHAND3`。
- Unicorn 检查了参数：按下位图 = {0, 1, 0, 0}，保持位图 = 0，其余三个参数为 0；并且不再调用 `0x103CE96E`。

### 第 3 次上机（`HO000081.BIN`）：合成函数返回 1，追踪仍不结束

- 8.46 s、16.43 s 各按了一次，合成函数都返回 1（放进队列成功），但追踪照常进行。

  - 没出现：取景时按键走的是另一条路，需要另找。

### 第 4 次上机（`HO000076.BIN`）：真实 OK 在环形缓冲区里，找到差别

- 亲手按的 OK 出现在输入环形缓冲区里，格式和合成的一样：第 2 个按键字 = 0x1，新按下位 = 0x1（如 5.00 s、6.12 s、9.76 s 的几格）。所以取景时按键**确实**经过这个缓冲区。
- 差别：真实的每一格里，第 1 个按键字始终是 **0x200**（某个一直处于开启状态的开关），半按快门时是 0x80000200。第 3、4 版把"保持位图"传成全 0，相当于告诉相机"0x200 松开了，同时按下 OK"。
- 第 5 版：合成前读出环形缓冲区最新一格（`0xC182004C` 的第 0 个字节是下一次写入的位置，最新一格是它减 1）的 4 个按键字（+4、+0x18、+0x2C、+0x40），去掉 OK 那一位后作为"保持位图"传入。按下时用的这 4 个字也记进日志（`AFHAND5`）。
- 这一轮模块一次都没按：人脸靠近时（33.5–34.3 s）人脸状态是 0x100（低字节 0），而且大约每 3–6 个 tick 才检测到一次。第 5 版改为：
  - 状态低字节 ≤ 2 都算"检测到人脸"（4 = 没有人脸）；
  - 连续 10 个 tick 都没检测到才清零（原来是 5 个）。
- 回放：`HO000076` 在 34.29 s 触发；`HO000081` 在 8.46 s、16.43 s；`HO000087` 在 13.23 s、22.53 s、28.37 s；`HO000093` 在 5.34 s；`AF000299` 在 45.78 s。都在人脸靠近追踪框的时段。

### 第 5 次上机（`HO000044.BIN`）：带上按住的键也无效，找到来源字段

- 4.32 s 按了一次；按住的键是 0x80000200（正在半按快门）。
- 合成的两格（[13]、[14]）开头那个字是 **0**，而所有真实按键的这个字都是 **0xC1818814**，推测是输入来源。原厂合成函数会把整份输入状态清零，所以设置不了它。
- 第 6 版不再用原厂合成函数：直接复制环形缓冲区最新一格真实输入的 0x18C 字节（来源字段和其他内容都保留），把 4 个按键字（每个字依次是当前值、上次值、变化、新按下、新松开，分别在 +4、+0x18、+0x2C、+0x40）改成"都不变"，只把第 2 个按键字改成"OK 按下"，交给原厂输入写入函数 `0x102F0D14`；写入成功后再调用 `0x102F1844`，这是原厂合成函数内部的调用顺序。然后再送一格"OK 松开"。日志里返回值的 bit0 表示"按下"成功，bit1 表示"松开"成功（`synth 3` = 两格都写入了）。文件头为 `AFHAND6`。
- 半按快门时，原厂可能本来就不理会 OK。测试时等模块按键的那段时间不要半按。

### 第 6 次上机（`HO000048.BIN`）：**生效**

## 第 4 份日志（af_log 第 4 版，`AF000078.BIN`，1097 个 tick）：追踪怎么开始

- `0xC23AA028`（= `0xC23AA02C`）在追踪期间每帧更新，是追踪器当前位置的粗网格（低 16 位 X，高 16 位 Y）。和追踪框对照（`AF000299`）：框中心 ≈ X × 32.4、Y × 34.4（追踪单位）。人脸框 1 格 ≈ 106 单位，所以人脸中心换算到这个网格是 X = (2x + w) × 1.636、Y = (2y + h) × 1.541。
- 追踪开始时画面里已有人脸（31.35 s、50.40 s）：追踪照样从中央开始，原厂不会自己锁到人脸。

静态反汇编没能直接找到"在指定位置开始追踪"的入口（追踪器代码在 `0x100AB000–0x100AE000`，结构体只通过基址加偏移访问）。所以第 8 版先做最直接的实验。

## 第 13 版：找到"每帧选 AF 模式"的代码，记录它的输入（af_log 第 6 版）

### 第 2 次上机（`AF000166.BIN`，第 15 版）：找到对焦结果

2032 个 tick（110 s）。标记脉冲只在最后几段出现，按内容分段：5–12 s、16–23 s、23–30 s、32–39 s、41–44 s、52–54 s 是人脸主体 AF（模式 0x203）后转身；55.5–72.9 s `0xC237F67C` = 1（AF-S），半按 3 次；72.9 s 起 AF-C，半按 2 次；92 s 起画面 1 / 跟踪。

- 它在 AF 选模式那一侧（`0x10074214` 附近读写），界面画框用的是 AF 发过来的消息；下一步要找实时取景画对焦框的代码和它取颜色的地方，再按这个结果选白 / 绿 / 红。
- **背身**：这几次人脸主体 AF，人脸检测丢失（主体数变 0）后 0.06–0.3 s 内就回到普通自动区域 AF（模式 0x200），AF 这一侧没有看到"等几秒"的计时。第 14 版之前那份日志里唯一一次"主体框变成跟踪框"（`AF000148` 7.70 s，0x203 → 0x202）发生在半按期间。也就是说，没半按时人脸一丢就回普通 AF；半按时交给跟踪器。要"延长"，需要在人脸刚丢失时继续沿用上一次的人脸位置一段时间，而不是改某个现成的超时常数；需要先确认用户看到的是哪一种情况（半按还是没半按）。
- 用户说明（2026-11-14）：不是让人背身，而是对着屏幕上的人脸，把相机移开，让主体框变成跟踪框。`AF000166` 里这几次都没有半按，所以人脸一丢就回普通 AF；半按时才会变成跟踪框（0x203 → 0x202）。下一份日志专门测半按中的这一过程，量出从人脸丢失到变成跟踪框的时间，并找这段时间由谁决定。

### 第 3 次上机（`AF000163.BIN`，第 15 版）：半按中人脸丢失

2317 个 tick（90 s），AF-C，对着屏幕上的人脸半按，把相机移开。

- 三次半按中人脸主体 AF（16.6–27.3 s、52–64.8 s、74.3–85.2 s）：人脸检测丢失（主体数 1 → 0）的同一个采样里，AF 选模式就从 0x203 变回 0x200（普通自动区域 AF-C），`0xC237F6A0` 0x100 → 0 在 0.06–0.17 s 后；没有出现跟踪器模式 0x202，也没有看到任何"等一段时间再放弃"的计时。

## 第 17 版：OK 的键码、界面里的对焦框列表（af_log 第 8 版）

### 第 1 次上机（`AF000102.BIN`，第 17 版）

### 静态分析（2026-11-14，接第 17 版）

- 拍摄画面的事件分派 `0x102AF960(事件号 < 0x14, 参数)`：事件 0 → `0x102AF8B2`（进入拍摄画面的初始化，里面对键 0x1B、0x1C 调 `0x10460D56` 清掉按键计时槽），事件 1 → `0x102AFC8E`，事件 3 → `0x102AFBE8`（读按键，键码存 `[参数+4]`），事件 6 → `0x102AFBC8`，事件 9 → `0x102AFB0A`，事件 11 → `0x102AF54E`，事件 12 → `0x102AF182`，事件 18 → `0x1045BF8A`，事件 19 → `0x102AF4A0`。
- `0x10460D1C(键, 值, 参数)` / `0x10460D56(键)`：每个键码一个槽（共 0x2E 个），记下时间，像是长按 / 连发计时，不是"键 → 动作"的映射表。
- 画面 1 时变 1 的 `0xC1821A98` / `0xC1821AA0` 是 `0xC1821A84` 起 5 组 {编号, 值} 表里的值（设置函数 `0x10455FC0(编号, 值)`），是取景画面上某些显示元素的开关，是进入画面 1 的结果而不是入口。
- 还没有找到"按键码 0x1B 分派到进入跟踪模式"的那一处；`0x102AFBE8` 存下的键码由后续事件处理，需要继续往下追。
- 对焦框：写 `0xC237C6A4`（= `0xC237C380 + 0x324`）的是 `0x10191610`，写入的是 `[r4+0x28C]`，随后用它作循环次数复制矩形（`0x10191616..0x1019163A`）：它是**要画的对焦框个数**，不是颜色编号（AF-S 对上 1 个、没对上 0 个；AF-C 对上 2 个、没对上 1 个）。颜色要在界面画框代码里找。

### 方法 B：找到"进入跟踪模式"（2026-11-14）

- 从第 13 版的 `0xC259FF28`（画面 1 时为 1）往回找：`0xC259FF0C` 起是 AF 侧的跟踪模式状态，`+0x10`（`0xC259FF1C`）0 = 空闲、1 = 画面 1（框已显示）、3 = 主体、4 = 跟踪中。在自己的互斥锁（`0x1021CD76`）下改它的有三个函数，通过 AF 接口 `0x10162F10 / F14 / F18` 暴露：
  - `0x100774F4`：状态 < 4 时设为 1（进入跟踪模式，画面 1）；
  - `0x1007756E`：设为 4（开始跟踪）；
  - `0x100775C6`：清零（退出）。
- 包装：`0x10230832(&字节)`（先 `0x1019596E` 检查，再 `0x1022FBF4` 发消息 0x40，然后进入）、`0x10230856()`、`0x10230866()`；界面一侧 `0x1045A1AE(&字节)`、`0x1045A1E6(0)`、`0x1045A21C()`（各记调试日志 0x3B / 0x3C / 0x3D）。
- **取景画面的 OK 处理 `0x10368B6E`**：`r4 = 0x1044DC5A()`（跟踪状态 0–3），键码 0x1B 时：状态 0 / 1 → `0x1045A1AE(&0)`（进入跟踪模式），2 → `0x1045A1E6(0)`（开始跟踪），3 → `0x1045A21C()`（退出，失败则进入）。`0x10458DC0` 是原厂"先退出再重新进入"的写法（`0x1045A21C` 后 `0x1045A1AE(&1)`）。
- 3D 跟踪第 4 版（v36）据此实现：半按中发生转主体时，在 3D 跟踪的设置块 `+12` 记下"待返回"；之后检测更新时，若画面 1 已经出现（原厂自己回去了）就清掉；若半按已松开（`F680` = 0）、不在跟踪（`F688` = 0）、画面 1 没出现，就像 OK 键一样调用 `0x1045A1AE(&0)`，然后清掉。按 OK 开始的跟踪不记"待返回"。

### 对焦框颜色：数据通路（2026-11-14）

- `0x101925CE(目标)`：把 `0xC237C7B4` 起 0x468 字节的 AF 显示数据整块复制出来（`+0x50` = 对焦结果 `0xC237C804`，`+0xC0` 起 = 框坐标 `0xC237C874`，`+0x348` = 框个数 `0xC237CAFC`）。界面包装 `0x104B9348`，有二十多个调用者。
- `0x10354524`：读 `+0x50` 决定对焦提示音，不是画框。
- `0x10367860` 一带：把这份数据和许多别的状态一起拼成取景显示信息结构（`r6`，例如 `+0x33C` = 对焦结果、`+0x340` = `+0x78`），交给取景画面绘制。下一步顺着这个结构里的对焦结果字段，找到真正画对焦框、选颜色的函数。

### 对焦框颜色：静态分析走不通的地方（2026-11-14）

- `0x10367260` 起的函数把取景显示信息写进两份 0x384 字节的结构：`0xC2016DEC`（这一次）和 `0xC2016A68`（上一次）。对焦结果在 `+0x50`（`0xC2016E3C`）。
- 用到 `+0x50` 的只有 `0x103057EA`：逐个比较两份结构里的 `+0x2E5 / +0x2E4 / +0x2B4 / +0x2B5 / +0x2CC / +0x50 / +0x2DD / +0x2DC / +0x170 / +0x174`，有不同就返回 1。它的两个调用者 `0x10311726`、`0x104BF920` 据此决定要不要重画，本身不画框。
- 整块复制对焦数据的 `0x104B9348` 的 30 个调用者里，同时读对焦结果和框坐标的没有找到；`0x103669EA` 读框个数，但做的是 AF 点选择。

### 第 1 次上机（`AF000207.BIN`，第 19 版）：原厂只在主体落在跟踪框上时才转

169 s，十几次半按跟踪。3D 跟踪的标志很快就置 1，但真正转成主体（追踪中模式变 0x203）只有 3 次（44.7 s、58.4 s、165.1 s），3 次人脸中心和跟踪框中心都相差不到约 200 个跟踪单位。11.96 s 等很多次人脸在"标准"范围内（左右约 1000、上下约 500）也不转。结论：原厂要求主体基本落在跟踪框上，3D 跟踪的范围只能更严不能更宽；要让"标准"生效，得找到原厂比较位置的地方（半径或用的位置）。

## 第 20 版：所有主体的列表（af_log 第 10 版）

用户希望把所有识别到的主体都画出来（选中白色、其他灰色）。原厂只画一个框，多个眼睛时显示左右箭头。

- `AF000095.BIN`（第 19 版，同时 1–5 个主体）：`0xC237E2E8` 的 0xF0 字节不是逐个主体的列表（4 × 15 个数，布局和主体数无关），`0xC237F624` 只有选中的那一个。
- 触摸主体搜索 `0x10073C76` 遍历的列表在 `0xC259EF18`：`+0x38` 个数，从 `+0x3C` 起每个 0x40 字节（`+0x40` 种类，`+0x42` x/y，`+0x46` 宽高）。`af_log -DLOG10`（`AFLOG10`）记录这块 0x300 字节和选中的人脸框。研究 EG 和 log9 相同。

### 上机步骤（第 20 版）
