# 怎么定位 CMOS 读出模式：Z30 C 1.20 的定位方法与本机结论

日期：2026-10-30。全部为本地静态分析与隔离执行，未访问相机、未修改固件。

## 先给结论

**Z30 的 CMOS 读出模式不在 EG 主镜像里，而由独立的 Cortex-M MCU 执行。** 这是本轮实证的结论，不是推测：

| 证据 | 内容 |
| --- | --- |
| 模块构成 | 更新包解码后是三个模块：`eg2090_0120a0.bi`（33.9 MB，ARM926 主程序）、`ex2090_012000.bi`（512 KB）、`_tpj04_v10a5.bin`（32 KB） |
| EX 模块身份 | 前 8 字节 `08 0c 00 20 / b5 02 00 08`：初始栈 `0x20000C08`、复位向量 `0x080002B5`，是标准 Cortex-M 向量表；含 STM32 系 RCC 寄存器 `0x40023840/0x40023844` 与 APB 外设窗口 `0x4000xxxx` 共 6000+ 处字面量 |
| EX 模块内容 | RTOS 对象名 `McuCmMtx`（MCU 通信互斥）、`McuMgCyc`、`LnMngSem`、`BatCmCyc`、`ShterAlm`、`SwichEvF`、`PowMgCyc`：MCU 通信、镜头管理、电池、快门、开关、电源管理 |
| EG 侧只有服务名 | 服务注册表（156 条，`0x12069BE0`，stride 0x18）里有 `CaptureSensorSer`（id `0x202`），但它只是**协议服务名**，代表“向传感器侧发命令的接口”，不含读出时序 |
| EG 侧没有读出表 | 全镜像搜索 3840/5568/3128/1120 等尺寸与 2997/5994/60000 等帧周期常数的共现，无任何 4K 50/60 读出配置；`readout`、`MIPI`、`LVDS`、`pixel clock` 等关键词零命中 |

所以想改 4K60 的读出模式，改 EG 是改不到的。需要动的是 EX 模块（或更下游的传感器固件），而 EX 是裸机 MCU 固件，改它等于重写 STM32 侧的驱动。

## 通用定位方法（可复用到其他机型）

定位“读出模式”不要从字符串开始找——读出时序通常不叫 readout。按下面五步走，每步都有可判定的产出。

### 第 1 步：先分清模块职责，别在错的文件里找

更新包是容器，先解码再分模块，然后判断每个模块的 CPU 架构：

- **ARM926 主程序（EG）**：跑 Linux 类应用层、菜单、编码器参数、封装器。特征是有大量 ASCII 文件名（`MovieRecordApplicationService.c`）、eDSID 设置项字符串、服务注册表。
- **Cortex-M（EX）**：裸机/RTOS，直接操作外设寄存器。特征：文件头是向量表（前 4 字节是 `0x2000xxxx` 栈顶，第 2 字是 `0x08xxxxxx` 复位向量）、大量 `0x4000xxxx` 外设字面量、RTOS 对象名。

判断方法：读前 16 字节。`0x2000xxxx` + `0x08xxxxxx` 就是 Cortex-M。这一条能省掉大半无效搜索。

工具里已实现：`tools/inspect_sensor_readout.py` 的 `ex_module_role()`。

### 第 2 步：在 EG 里定位“模式表 → 选择器 → 消费方”三件套

读出模式的**上层输入**一定在 EG 里，因为菜单和录像参数在主程序。定位顺序：

1. **模式表**：找 30 条 × 0x1C 字节的连续记录，每条含宽、高、时间基、帧时长、GOP、最大/平均码率。Z30 在 `0x10713154`。
2. **选择器**：找按 `(分辨率码, 帧率码, 画质)` 三分支 switch 的函数。Z30 在 `0x1035566C`。反汇编后能直接读出每个分辨率分支支持哪些帧率码——这是判断“固件在参数层砍了什么”的最快方法。
3. **消费方**：全量扫描 Thumb `BL` 指令建调用图（不要只搜字面量池，BL 是直接编码的）。Z30 的 6 个消费方分别是剩余时间估算、编码参数、封装器配置等。

这一步的产出是“参数层的完整缺口清单”。Z30 的结论：4K 分支只测帧率码 2/3/4，码 0/1（59.94/50）无目标记录，落默认值 6。

### 第 3 步：用编码器构造器验证硬件边界（决定是否值得继续）

参数层能改不等于硬件能做。用 Unicorn 跑原厂构造器，喂不同尺寸/帧率的合成输入，看它算出的 level：

- 若构造器对 4K 高帧率仍输出 Level 5.1，而 Level 5.2 只存在于查表辅助里，说明参数栈按 5.1 封顶构建。
- 再算像素率：把固件里所有已有模式的数据率列出来，看峰值。Z30 全部模式都顶在 ~249 Mpx/s（4K30 与 1080p120 同值），恰是 Level 5.1 的 251.66 Mpx/s 上限；4K60 需要 498 Mpx/s，正好 2 倍。

**这一步是分水岭**：如果峰值已经是规范上限的整数倍关系，说明原厂是按某个硬件吞吐上限设计的，4K60 大概率不是“没开”而是“做不到”。

### 第 4 步：在 MCU 侧找读出配置（真正的工作量所在）

确认读出在 MCU 侧之后，在 EX 模块里按这个顺序找：

1. **外设窗口**：STM32 的 RCC（`0x400238xx`）、GPIO、SPI/I2C、DCMI/CSI 控制器。统计字面量分布能快速判断用了哪些外设。
2. **命令表**：MCU 通信通常有一张 `(命令 id, 参数长度, 处理函数)` 表。找 `McuCm*` 系列对象名附近的函数指针数组。
3. **帧同步信号**：读出模式的核心是行/帧时序（HTS、VTS、曝光行数）。找写定时器寄存器（STM32 的 TIM `0x4000xxxx`）的代码，参数通常来自一个结构体，结构体由上层命令填充。
4. **反向确认**：在 EG 侧找 `CaptureSensorSer` 的调用点，看发给它的命令 id 有哪些。EG 里的命令 id 和 EX 里的处理表能对上，就找到了完整的下发链路。

Z30 的情况：EG 侧只有服务名和注册索引，没有可用的命令表结构；EX 侧有 MCU 通信代码和外设访问，但读出时序参数没有以可识别的平铺表形式出现——很可能由 MCU 内部按命令计算，或固化在传感器自身的寄存器初始化序列里。

### 第 5 步：判定可改性

| 现象 | 判定 |
| --- | --- |
| EG 里有读出模式表，且 MCU 只做转发 | 可改，补表 + 补选择器分支即可 |
| EG 里没有表，MCU 有完整命令处理 | 需改 EX 固件，工作量大但可行 |
| 传感器初始化序列固化在 MCU 或传感器 ROM | 基本不可改，除非能重写整条初始化链 |
| 像素率已达规范上限整数倍 | 硬件不支持，改固件无意义 |

Z30 落在第 2~3 档之间：读出控制确定在 MCU 侧，但缺少可识别的参数表，无法判断是“MCU 计算”还是“传感器固化”。

## 复现

```powershell
python tools/inspect_sensor_readout.py --source Z_30_0120.bin --output build/research/sensor-readout.json
```

输出包含：三模块大小与哈希、EX 模块架构判定（向量表 + STM32 外设字面量计数）、30 条模式表记录、选择器各分辨率分支的帧率码、`CaptureSensorSer` 在服务注册表中的索引。工具内的断言会校验 4K 分支只有 2/3/4、1080 分支含 0~4、720 分支含 0/1——若某次固件更新改变了这些，工具会直接报错而不是给出错误结论。

## 如果要做下去

按投入产出排序：

1. **先确认值不值得**：用相机录一段 4K30，看编码器实际吞吐与发热。若已接近散热极限，4K60 即使能开也不可持续。
2. **反汇编 EX 的命令表**：这是唯一能确定读出是否可改的路径。需要完整反汇编 512 KB 的 Cortex-M 固件并定位 `McuCm*` 命令分发。
3. **找传感器型号**：拆机或从 MCU 初始化序列的寄存器地址反推。拿到型号后查 datasheet 的读出模式列表，能直接回答“支不支持 4K60 读出”。
4. **不要从 EG 补丁入手**：EG 侧改完只会让菜单多一个 4K60 选项，实际录制仍走 MCU 的 30p 读出，结果是 60p 容器装 30p 内容或直接失败。
