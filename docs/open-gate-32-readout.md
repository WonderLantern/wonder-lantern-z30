# Z30 C 1.20：3:2 24p（open gate）读出研究

日期：2026-11-04。全部为本地静态分析，未访问相机、未修改固件、未生成补丁。

## 结论

1. **更正此前结论：CMOS 不由 EX 模块驱动。** EX 是副控 MCU，RTOS 对象只有电池、镜头、时钟、快门、按键、电源，全模块没有任何成像相关字符串。CMOS 由主程序 EG（双核 Cortex-A7）经 SIO 通道 5 的串行口直接驱动。[sensor-readout-locating.md](sensor-readout-locating.md) 里"读出在 MCU 侧、要改 EX"的判断作废。
2. **CMOS 的模式寄存器序列不在升级包里。** 驱动把整块"驱动数据"（数据区 0x4C，约 1.4 MB）当作寄存器包来源，这块数据在运行时从机身 NOR 闪存 bank 26（`0x13E80000`，1.5 MB）读入。EG 所在的可升级 bank 止于 `0x12960000`，升级包里只有 EG/EX/TPJ 三个模块，所以**离线拿不到任何读出模式的寄存器值**。
3. **3:2 24p 现在还不能做成补丁**，但难度比之前判断的低很多：不用重写 MCU 固件，可以在 EG 里拦截寄存器序列写入函数，在 RAM 里替换要发出的包，完全不碰闪存。前提是先在实机上把驱动数据读出来。
4. 行率上 3:2 24p 不比现有 4K 30p 更吃力（见下文），所以硬件不是第一道墙。真正卡住的是驱动数据和传感器寄存器的含义。

## 为什么 3:2 24p 值得研究

若传感器读出速度受每秒读出行数限制，且 open gate 用与 4K 相同的行密度：

| 模式 | 每帧行数 | 帧率 | 每秒行数 |
| --- | --- | --- | --- |
| 4K 30p（16:9，现有） | 3128 | 29.97 | 约 93,700 |
| 3:2 24p（open gate） | 3712 | 23.976 | 约 89,000 |

3:2 24p 的行率比现有 4K 30p 还低约 5%。编码侧 3240×2160 24p 约 168 Mpx/s、27,405 个宏块，都在原厂 Level 5.1 的上限内（见 [uhd-4k60-feasibility.md](uhd-4k60-feasibility.md)）。

这里有个未经验证的前提：4K 模式实际每帧读多少行（是否隔行跳读）要等拿到驱动数据才知道。如果 4K 是满行读出，上表成立；如果是跳行读出，open gate 也必须用同样的跳读方式。

## 证据

复现：`python tools/inspect_cmos_driver.py --source Z_30_0120.bin --output build/research/cmos-driver.json`。脚本对下列每一条都做断言，固件不符就直接报错。

### SoC 结构

EG `0x105B2B16` 起是一张 32 字节一条的中断名表，列出了整个 SoC 的硬件模块：

- CPU：`CA7_CPU0/1`（EG 运行的核）与 `A926`（协处理器）。
- 成像链路：`SIF_0..7`（Sensor InterFace）、`PPC_0..4`、`RAW`、`RAWRS`、`IPU`、`IIP`、`H264`、`JPEG_ENC`。
- 串行口：`SIO_0..10`、`I2C_0..3`。

EG 内嵌的 ARM926 镜像（向量表在 `0x11C9E69C`，加载到 `0xC1000000`）只有 Wi-Fi、蓝牙、SD、TCP 等代码，是无线子系统，与传感器无关。

### CMOS 串行驱动（SIO 通道 5）

| 地址 | 行为 |
| --- | --- |
| `0x1019D748` | 上电：配置 4 个 GPIO（`0x17/0x19/0x18/0x1A`），打开 SIO 通道 5 |
| `0x1019D7D6` | 设置时钟：5 MHz 或 20 MHz |
| `0x1019D868` | 写：按 ≤0xC0 字节分块发送，片选由 GPIO 控制 |
| `0x1019D91E` | 读：先发 `0x82, 地址高, 地址低`，再读回数据 |
| `0x101401F6` | 序列写入：给一块拼接好的包和一个以 0 结尾的 u16 长度数组，逐包调用写函数 |

读命令格式（芯片 ID 字节、读操作置 bit7、两字节地址）和 Sony CMOS 的 4 线串行协议一致，但传感器型号尚未确认。

`0x101400D0` 用常数 `72,000,000`（疑似传感器输入时钟）和 `1e9` 把驱动数据里的行周期字段换算成时间，是曝光/读出时序计算的候选入口。

### 驱动数据来源

| 环节 | 位置 | 内容 |
| --- | --- | --- |
| 初始化 | `0x100F0DC8` | `movs r0,#0x4c` → 取数据区地址 → `0x101139A0` |
| 保存指针 | `0x101139A0` → `0x10139E84` | 写入驱动上下文 `0xC18E4FEC + 0x14` |
| 数据区描述 | RAM `0xC1880D2C + 0x4C×28` | 大小 `0x168000`，地址运行时填入，bank 26 |
| NOR bank 描述 | RAM `0xC1880888 + 26×44` | 地址 `0x13E80000`，大小 `0x180000`，有效载荷 `0x17FFFC` |
| EG 所在 bank | bank 2 | `0x10020000`，大小 `0x2940000`，止于 `0x12960000` |

驱动读取这块数据时用到的偏移在 `0xE0000..0xF0000` 之间，按命令类型和驱动模式查表：`0x11C57A84` 是 `[命令×14 + 驱动模式]` → 数据记录的索引表，**传感器共有 14 个驱动模式**。哪个驱动模式对应 4K、1080p、120p 和照片取景，还没有恢复。

QEMU 项目此前已独立确认这套 bank 描述符的寻址方式和 NOR 写入路径（扇区 0x20000，先擦后写）。

### 已排除的候选

- `0x10690518` 有一张 4247 项 `(u16 地址, u16 值)` 默认值表，驱动在 `0x10122B2E/0x10122B90`（SPI、读地址置 `0x8000`）。它是**音频编解码器**：配套查表是 1–35 级音量和 0–20 级增益，寄存器值是成对的滤波器系数。
- `0x115A4C80` 的 `5656×3918 / 5568×3712 @ (72,198)` 和取景尺寸 `1400×932 / 1400×794` 是 EG 侧的图像几何表，不是传感器寄存器。

### 它做什么、不做什么

- 菜单：**设置菜单 → Extensions → CMOS data dump → Save CMOS data**，按 OK。完成后回到 Extensions 页，右侧显示结果。

- 不写传感器、不写驱动、不写 NOR、不改任何设置；拍摄和传感器代码路径上没有任何钩子。唯一新增的代码只在按下菜单项时运行。

| 结果文字 | 含义 |
| --- | --- |
| Saved WL-CMOS.BIN | 成功，文件 1,474,960 字节 |
| No CMOS data | 指针为空、未对齐或超出范围，没有读任何数据 |

QEMU 里驱动数据指针是 `0xC85BB700`，与数据区 0x4C 描述符 `+8` 的地址字相同，印证了静态分析的链路。模拟器没有 bank 26 的内容，那块数据全是 0；真实内容只能在机身上取。QEMU 不挂载虚拟卡，原厂文件服务在无卡时不会应答，所以模拟器检查替换了打开/写入/关闭三个服务；路径设置、分配器和 memcpy 是原厂代码。

开发中踩到的一个坑：扩展框架会在页面首次进入时把状态区 `fd_offset` 处（默认 +4）写成 -1。第一版把 +4 当缓冲指针，导致 memset 写到 `0xFFFFFFFF` 触发数据中止，原厂异常处理随即尝试把崩溃日志写进 NOR。现在页面把真正的 fd 位置报给框架，QEMU 真实启动流程下已确认不再发生。

### v1 的问题：SD 写出读到了旧内存（已在 v2 修复）

第一次机身测试（v1 构建）导出了三份文件。大小、指针（`0xC8500000`）、数据区与 NOR 描述符都正确，但每份的累加和都与写出内容不符，三份之间约 52 万字节不同。证据指向缓存一致性，而不是数据本身在变：

- 三份里唯一稳定的内容恰好是**每个 32 KiB 写入块的最后 256 字节**。
- 约 44% 的非零 64 字节行与**前一块同一偏移**逐字节相同，远超真实数据的可能。

也就是：CPU 把数据复制进回弹缓冲后，新内容还在 D-cache 里；SD 控制器用 DMA 从内存读缓冲，读到的是之前几块被挤回内存的残留。文件头的累加和是 CPU 读的，所以它反映的是真实数据。v2 在每次写出前调用原厂 `0x10204B0C(ptr, length)`（按 64 字节行 clean 到 PoC，结束 `DSB SY`），文件版本升为 2；读取工具会拒绝 v1 文件。QEMU 不模拟缓存，这一修复只能在机身上确认。

同样的问题可能存在于 JPG 预拍摄探针的导出（CPU 复制后直接写 SD），该功能未在机身上验证过导出内容。

### v2 机身结果（2026-11-04）

两次导出（中间关机重启）的累加和都与文件头一致，1,474,560 字节驱动数据逐字节相同，指针仍为 `0xC8500000`；驱动上下文只有 `+0x98/+0xA0/+0xC4/+0xCC` 四个运行时字不同。缓存修复在机身上有效，这块数据是稳定的。

驱动代码引用的偏移处确实是 CMOS 写包：`81 地址高 地址低 数据…`，配一张以 0 结尾的 u16 长度表（如 `0xE1400` 为 `81 00 D2 01`、长度表 `[4, 0]`；`0xE6030` 起是从寄存器 `0x0164` 开始的连续写入）。这些包集中在 `0xE1000..0xEFFFF`。数据区 `0xE0000` 起有一段逐台编号，文件不得外传。

## 驱动模式解码（第 2 步，进行中）

`python tools/decode_cmos_modes.py --dump-dir build/research/cmos-ab --output build/research/cmos-modes.json`：在 Unicorn 里对实机驱动数据执行原厂选择器 `0x10139F44(命令, 请求)`，拦截序列写入器 `0x101401F6` 记录要发给 CMOS 的包，并枚举原厂映射函数 `0x1013D7DE`。输出由逐台数据派生，只留在本地。

### 调用链

上层采集服务把消息字段 `+0x18/+0x19/+0x1A` 变成参数 `p0/p1/p2`（`0x100F1B02` 起，经 `0x100F0EA4`），拷入 `0xC239BCFC`；`0x10114308` 再用 `0x1013D7DE(p0, p1, p2, 0, p[0x27], 标志)` 算出请求 `0xC18E4EBC` 第 0 字节的**类型码 0–12**（该调用点第 5 个参数恒为 0，第 6 个是 `p[0x27]`）；`p[0x30]` 置位时直接取类型 2 或 3。模式切换序列 `0x10114674` 起依次发命令 4、15（条件）、6、7、13（条件）等。

| 映射结果 | 条件 |
| --- | --- |
| 0 | `p0=0`（其他未列条件）或 `p0=5` 且 `p2` 不为 1/2 |
| 1 | `p0=0, p1=2` |
| 4 / 5 | `p0=4`，或 `p0=0` 且 `p[0x27]=1`；`p1=2` 时为 5 |
| 6 | `p0=5, p2=2` |
| 7 / 8 | `p0=5, p2=1`；第 5 个参数 2–6 时为 7、0–1 时为 8。该调用点恒传 0，所以这里只会得到 8 |
| 9 / 10 / 11 / 12 | `p0` = 1 或 3 / 2 / 6 / 7 |

### 命令与包

29 条命令里，`cmd 4` 是主模式设置：34 个包、276 字节，13 种类型分成 10 组不同内容，174 个寄存器字节里 102 个随类型变化。其余多为开关量（`cmd 15/16` 一对、`cmd 17–28` 只在类型 4/5 下有效）。

候选解读（**未证实**）：`0x000A/0x000C` 两个 16 位字段在类型 6 为 308/3174，在类型 7/8 为 308/1058（= 3174 ÷ 3），其他类型为 106/1132。3174 ≈ 16:9 的 3128 行加余量，因此类型 6 像 4K 满行读出、7/8 像 1080p 隔行读出，`p0=5` 像录像、`p2` 像分辨率。但其余类型的 1132 用同样的解释对不上，必须用实机确认“菜单模式 → 类型码”后再下结论。

### 实机模式记录结果（2026-11-04）

按 照片 → 4K30 → 4K24 → 1080p60 → 1080p30 → 1080p120 → 照片 切换，记录到 11 次 `cmd 4`，类型码依次为 9 6 9 6 9 7 9 7 9 8 9（每次进菜单改档位都会先回到照片取景）：

| 菜单模式 | 类型码 |
| --- | --- |
| 照片取景 | 9 |
| 4K 30p、4K 24p | 6 |
| 1080p 60p、1080p 30p | 7 |
| 1080p 120p | 8 |

更正：参数块 `0xC239BCFC` 在这些切换时全为 0，类型码不是经 `0x10114308` 那条路径算出的；之前“这里只会得到类型 8”的推断不成立。请求结构里的类型码是实际生效的值，上表可靠。

只看真正用到的 4 种类型，`cmd 4` 有 48 个字节不同。窗口相关字段（u16 小端）：

| 模式 | `0x000A` 起始 | `0x000C` 行数 | `0x0000` | `0x0011` |
| --- | --- | --- | --- | --- |
| 照片取景（9） | 106 | 1132 | 0x1C | 80 |
| 4K（6） | 308 | 3174 | 0x0C | 160 |
| 1080p（7、8） | 308 | 1058 | 0x14 | 20 |

观察：

- 1080p 的 1058 = 3174 ÷ 3，起始行同为 308，且 308 + 3 × 1058 = 3482 = 4K 窗口末行。1080p 是同一 16:9 窗口每 3 行读 1 行，4K 是满行读出。
- 4K 30p 与 24p、1080p 60p/30p/120p 的 `cmd 4` 包完全相同。**帧率不在主模式包里**，帧周期由运行时按请求字段动态生成的命令设置，所以 24p 本身不是障碍。
- 照片取景若同样每 3 行读 1 行，则覆盖 106..3502（3396 行），比 4K 窗口多 222 行，接近 3:2 的高度。这只是推断，`0x0000` 和 `0x0011` 在三者间各不相同，模式位含义还没确定。
- 时序相关的 `0x0027/0x002A/0x042A–0x043E/0x0251` 等在照片取景与录像之间不同，录像三种类型之间相同。

据此，open gate 的最小传感器侧实验是：以类型 6（4K）的包为基础，把窗口扩到照片取景的覆盖范围（起始约 106、满行约 3396 行），帧率 24p。行率约 3396 × 23.976 ≈ 81,400 行/秒，低于 4K 30p 的 3174 × 29.97 ≈ 95,100 行/秒。

### 找 SIF 帧周期（第 6 步，进行中）

静态线索：
- CMOS 驱动模块自称 TG（`0x10113D6C` 字符串 `TgDebug`），其后紧跟一组负数计数预置 `0xFFFFDA07/E4BB/F843/F45B/F073`，像定时器通道预置。
- 该模块最常用的外设基址：`0x20380000` 块（由 `0x1011B000–0x1011D000` 配置，QEMU 照片取景中写入 `0x20380048 = 1398×932`、`0x203800C4 = 1398`，像传感器数据接收端 SIF）和 `0x20200000` 块（写入的多为缓冲地址，像 DMA/统计）。
- `0x20060000` 块由 `0x101225xx` 配置，紧挨音频驱动，排除。`0x20068000` 是采集/ISP 门控与中断。定时器外设在 `0x2C011000`（12 通道）。

| --- | --- | --- | --- |

### SIF 扩展页（cmos-ptp3）

`0x20381000–0x20386000` 有 700 个非零字，`0x20386000–0x20390000` 全为 0（未实现）。4K30 连读两次一致；4K30 与 4K24 之间只有 `0x20381A4C–0x20381A58`、`0x20381A8C` 五个值差 1–3（像曲线/统计）。

**阶段结论**：取景待机状态下，4K30 与 4K24 在传感器 SPI、SIF 全部 6 页、CMOS/TG 块、采集块、定时器中都找不到帧周期差异，唯一稳定差异是 `0x0007`（984 vs 127）和 SIF `0x203800F0`（4K30 为 `0xFC48E`，4K24 与照片为 `0x8E`，各只采样一次）。

待验证的解释：录像待机时取景可能以固定预览帧率运行，按下录制后才切换到 24p/30p 的实际时序。下一步在**录制过程中**采集 SPI 流和寄存器快照，对比 4K30 与 4K24 录制时的差异。

### 录制中采集（cmos-ptp4）

实机发现：插着 USB 无法录像；录制开始时相机会从 USB 断开，结束后需重新插线。录制前后模式记录出现连续的类型 6→6（不换档位却重复下发主模式包）以及类型 8，疑似对应录制开始/结束，但对应的 SPI 记录在重新连上前已被取景逐帧写入覆盖。

cmos-ptp4 让 SPI 日志按寄存器去重：每个寄存器（按地址散列到 64 槽）记住最近两次写入的“标签 + 前 24 字节”，新包与其中任一相同就不记录（能过滤 `0x0007` 的逐帧交替），Arm 时清空历史，文件版本 3。Unicorn：7 项通过，其中把 USB 实采的 2,000 个真实 4K30 逐帧包送入钩子，只记下 12 条且与 Python 模型一致；另有 1,046 次合成写入时输出与原厂完全一致。QEMU 固件版本页（三种语言）与页面检查全部通过。

用法：拔掉 USB → Arm → 录 4K30、4K24 各几秒 → 插回 USB → `cmos_live.py` 读环形缓冲与模式记录，不再需要赶时间或存卡。

### 录制中采集结果（cmos-ptp4，2026-11-04）

拔掉 USB 录制 4K30、4K24 后插回读取：整段去重 SPI 日志只有 1,086 条，未被覆盖。模式记录为类型 9 之后连续 6 次类型 6。

- SPI 日志只有两个完整 `cmd 4` 块（照片第 17 条、4K 第 82 条）。其余 5 次类型 6 下发与第 82 条逐字节相同，被去重过滤。**录制开始/停止、30p 与 24p 录制，发给传感器的主模式包完全相同。**
- 每次切换只多出一小段固定包：`0042=66`、`011B=00`、`08BD=EE66`、`0A2B=0x0018×4 或 0x0030×4`（交替）、`0003=0000`、`08BD=66`，共 5 次。`0x0A2B` 像录制状态开关，不像帧周期。
- 其余为逐帧自动曝光：`0x001D/0x0893` 是平滑变化的增益，`0x08BF` 在 `0404/0000` 间周期切换。整段没有帧长类数值。

**结论：取景与录制下，30p 与 24p 的传感器 SPI 内容都相同，帧率完全由 SoC 侧决定。** 录制时 USB 断开，无法实时读 SoC 寄存器。下一步：固件在录制中定时快照 SIF 与 CMOS/TG 块到内存环形缓冲，录完再读出对比。

- **`0x000A` 是读出起始行**：起始提前 202 行（约 6% 画面高），而下游仍按原行数截取，所以截到更靠上的一段。

- `0x000C` 是否就是行数还无法单独确认：多读的行被下游丢弃，画面上看不出差别。

下游截取 3174 行的位置已经找到：

| 位置 | 内容 |
| --- | --- |
| 采集块 `0x2006850C` | `0x0C66_15E0`（3174 × 5600） |
| `0x20069D00/04`、`0x20069E78`、`0x2006BA08/0C` | 3174、5600 |
| `0x2006B0B4` = 3136，`0x2006B180/184` = 3840 | 疑似 16:9 输出裁切高度与 4K 输出宽度 |

下游链路：传感器窗口 → 采集原始尺寸（5600×3174）→ 缩放（3174 → 取景 794 / 录像输出）→ 编码器尺寸。

### 采集尺寸跟随窗口（cmos-window2）

CMOS 驱动里的 `0x10132128(请求, 尺寸输出, 偏移输出)` 按采集编号返回传感器原始尺寸：编号 0/12/14 为 5600×3728（照片全幅），3 为 1864×1242（照片取景），**4/8 为 5600×3174（4K）**，5/9/11 为 5600×1058（1080p）。兄弟函数 `0x10132190` 返回输出尺寸（如 5568×3128、1392×782），调用方 `0x101323xx–0x101326xx` 据此配置采集。`0x120053B4`（RAM `0xC1883720`）的 5600×3174 属于 `0x101DD800` 一带的插值/校准上下文，不是采集来源。

cmos-window2 包装 `0x10132128`：原厂执行后，若预设非 Stock 且结果恰为 5600×3174，就把高度改成预设行数（3238 / 3396）。其他尺寸与偏移不变；缩放表和编码尺寸尚未改动。Unicorn 9 项通过（新增：三档预设下 16 个编号 × 2 种标志的返回值，只有编号 4、8 的高度按预设改变），QEMU 固件版本页（三种语言）与页面检查通过。

## window5：下游采集记录

window4 实机读回：drive data 三处高度和 0x2006850C 已是 3396，但 0x20069D00、0x20069E78、0x2006BA0C、SIF 0x20380734 仍是 3174（或其一半 1587）。

来源追踪：0x20069D00 由 0x1012050E 写入（`ror16(*(u32*)rec)`），调用链 0x100B277C → 0x100CB8FA → 0x1012050E，rec 是 0x100B2670 里从 0x100F6630(code, variant) 返回的记录复制出的 24 字节。0x100F6630 查 ROM 表 0x115A81E4（每 code 一项 `{ptr,count}`，记录 0x178 字节，+0 高度、+4 宽度）；0x100F665A 查 0x115A8274（记录 0x94 字节，+0x16 高度，+0x1A LV 输出宽度 1400）；0x100F6CE0 读第一张表的 +2/+6。4K 记录：code 4 → 0x115A67E0 / 0x115A7B80，code 8 → 0x115A6C48 / 0x115A7D3C，高度都是 3174。

RAM 0xC188416C 起另有一组 60 字节记录（getter 0x101E5C74，5600×3174 / 5600×1058），调用者看起来是测光/对焦网格划分，暂不改。

window5 在这三个查找函数入口接管：Stock 原样返回 ROM 指针；选了预设时 4K 记录改为返回页面状态里的副本，副本只有高度半字换成预设行数。离线验证（verify_cmos_window.py，13 项）对 code 0..17 × variant 0..3 比较返回内容。镜像 output/cmos-window5（188fb47b…），QEMU 三语言固件版本页 0xC1839680 正常。

实机结果（window5，4K 24p，3:2 预设）：0x20069D00、0x20069E78 变为 3396；0x2006BA0C 仍 3174，0x20380734 仍 1587。画面与 window4 相同：大小不变、整体上移，没有拉伸或花屏；视频模式拍照顶部彩色条纹消失，照片、取景、录像内容一致，录像和回放正常。解释：传感器从第 106 行起输出 3396 行，下游仍只取前 3174 行，所以视野上移 202 行而不变大。

## window6：裁切窗口

0x2006BA00..0C（x、y、宽、高 = 0、0、5600、3174）由 0x1011FD80 写入，唯一调用路径是 0x100B1AA2 → 0x100CB682，参数是 RAM 结构 0xC266440C（+0x1E/+0x20/+0x22/+0x24）。window6 接管 0x100CB682：选了预设且结构为 5600×3174 时，传给写入函数一份只改了高度的副本，固件自己的结构不写。离线验证 16 项；output/cmos-window6（902535c0…），QEMU 三语言固件版本页正常。

实机结果（window6）：0x2006BA0C 变为 3396，画面仍只上移。0x2006B000.. 是色调曲线表，之前记下的 3136/3840 只是表项，不是尺寸。前端（0x20068000–0x2006C000）对比 window4 只有高度相关的变化（0x20069D18/D20 等随高度变化），前端 LV 输出 1400×794。

## window7：读后端通道 1

0x20380000 这一 IP 按通道重复，写入函数地址加 `通道 << 18`（列表写入 0x1011E734、SIF 0x1011D0C8 都这样）。通道 0 的 0x20384000.. 读回全 0，QEMU 只在通道 1（0x203C0000）写过初始化值，没有进入 4K 视频。window7 只在 USB 只读操作里加了 0x203C0000–0x203D0000 窗口，其余同 window6。output/cmos-window7（5ef7694e…），QEMU 三语言固件版本页正常，PTP 离线 21 项通过。

实机结果（window7，Stock 预设，4K 24p）：通道 1（0x203C0000–0x203D0000）64 KB 全读回 0，通道 0 的 0x20383000 起也全 0，判断这部分后端寄存器只写不读。RAM 里找到的 3840/3904 等值（0xC2BE34xx）是线性曲线表，不是尺寸；QEMU 里 0x20384AEC=0x0F400F00 也是同一类曲线表项。

更正：0x2006BA00 这一块是统计（AE/AWB）窗口，不是主图像裁切。它的描述结构（如 0xC2BFC768，步长 0xB8）里，5600×3174 后面跟着统计网格 1392×782 和窗口坐标 2258/430/…，这些坐标就是 0x2006BA34.. 的值。

前端 Stock 和 3:2 对比（window7 Stock 对 window6 3:2）：除 0x2006850C、0x20069D00、0x20069E78、0x2006BA0C 外，0x20068900 从 0x887 变成 0xD43（3395 = 3396−1，可能是行计数或中断行）；0x20069D18/D20（= 0x20069EDC/EE4）随高度变化；其余主要是曝光和统计在变。前端 LV 输出仍是 1400×794，但实机取景只上移、没有压缩，说明取景和录像用的画面不是由前端这个 1400×794 输出决定的，或者纵向缩放比例另有来源。

## 主图像路径线索

记录 b（表 0x115A8274，查找 0x100F665A）就是前端缩放配置：code 4 为 5600×3174 → 1400×794（取景，1/4），code 8 为 5600×3174 → 4000×2268（4K 录像中间图，1/1.4），code 5 为 1058 → 1400×794，code 0 为 3728 → 1400×932。字段 +0x16 输入高度、+0x1A 输出宽度、+0x6C 输出高度，+0x2C.. 为滤波系数。window5 起选预设时 code 4/8 的输入高度已是 3396，没看到直接存放的缩放比例。

如果硬件按输入/输出尺寸自己算比例，取景应是 3396 行压进 794 行（纵向压缩约 7%，顶边上移 202 行、底边只下移约 20 行），肉眼不容易和"整体上移"区分。需要固定机位对比 Stock 和 3:2 的录像帧来判断。

其他排除项：0x20380728..0x20380738（700×397、1587）这组属于统计块，配置在运行时 RAM（如 0xC234D2B6）；0x115A4C80.. 是照片尺寸表（视频模式拍照 16:9 为 5568×3128）；0x10713154.. 等是编码器表（3840×2160 + 帧率）。

## 固定机位对比与 window8

DSC_0432（Stock）对 DSC_0433（3:2，window7），4K 24p，取第 1 秒帧，在 x 1300..2300 的列平均亮度上拟合纵向缩放和平移：缩放 0.999，平移 164 输出像素，相关 0.9998。结论：不是压缩，确实只用了前 3174 行。

原因：记录 a（0x178 字节）+0xD0.. 和 +0x120.. 是横向、纵向的固定抽取相位模板（位掩码，周期 14–18 个输入像素，+0xEC/+0x13C 为每组末位标记，+0x108/+0x158 为系数）：code 4 为 4:1（0xFF/0xFF00），code 8 为 1.4（14 进 10），code 3 为 4:3，code 7 为 3:1。输出尺寸固定，多给输入行只会被丢弃。

window8：选了预设时，4K 取景的记录 b（0x115A7B80）输出行数 +0x6C 由 794 改为 预设行数/4（偶数，3396 → 848，3238 → 808），抽取模板不变（照片取景 3728 → 932 也是同一模板，缓冲至少能放 932 行）。录像（code 8，4000×2268）暂不改。离线 16 项通过，output/cmos-window8（5da625d7…），QEMU 三语言固件版本页正常。

实机结果（window8，预设 3:2 生效后读回）：0x20069ED4（前端取景缩放输出行数）= 848，但 0x2006920C、0x2006951C（取景输出 DMA，写入点 0x1012016E）和后端 0x20380048（写入点 0x1011BF52）仍是 794，取景仍只上移。

## window9：取景帧尺寸

取景帧尺寸来自 0x1020C010(aspect)，返回 ROM 表 0x115A4CC0 + aspect×4（3:2 = 1400×932，16:9 = 1400×794）。调用点 0x10143D62、0x10143EB6 用它算取景缓冲的行距（宽×1.5，16 对齐）和大小；另有函数指针 0x10A540EC。window9 接管这个函数：选了预设时 16:9 项返回 1400×(预设行数/4，偶数)，其余不变。离线 19 项，output/cmos-window9（bb3dc5fc…），QEMU 三语言固件版本页正常。

## window10：缓冲规划

0x2006951C 的写入函数 0x1012012C 由 0x100B1818 经 0x100CB7EE 调用，尺寸来自配置对象 +0x28/+0x2A。代码里 movw #794 只有 6 处，其中 0x10143DD4 属于缓冲规划函数 0x10143CD2(plan, settings)：输出 {类型, 行距 @2, 宽 @4, 高 @6, 宽 @8, 高 @0xA}，4K 视频时取景硬编码 1400×794（行距 0x840），录像中间图硬编码 4000×2268（行距 6000，分支 0x10143E36），1080 为 2800×1866/1058。window10 接管该函数：原函数执行完后，若规划为 1400×794 且预设生效，把高度（@6，以及 @0xA 若为 794）改为 预设行数/4（偶数）。离线 22 项，output/cmos-window10（ae1cc684…），QEMU 三语言固件版本页正常（照片取景同样经过该函数，开机正常）。

实机结果（window10）：取景链全部变为 848：0x20069ED4、0x2006920C、0x2006951C = 848，后端 0x20380048 = 1400×848，0x2038009C = 847。画面仍与之前相同。

## window11：显示裁切表

RAM 0xC18DCEA0 起的静态表（引用 0x100B9B40），每项 0x20 字节 {源宽, 源高, x, y, 裁宽, 裁高, 裁宽, 裁高}（u32）：照片 3:2 为 1398×932 → 1388×926；4K 取景两项为 1400×794 在 (2,2) 裁 1390×782 / 1392×782；4K 录像中间图 4000×2268 在 (6,8) 裁 3976×2236；1080 为 1866×1058 → 1856×1044。显示从 848 行的帧里只取 (2,2) 起 782 行，所以仍只看到上部。

window11：Window test 每次切换时，把两项 4K 取景的源高和裁高按预设改写（794/808/848，782/796/836），只改认得的值，Stock 恢复。这张表在 RAM，重启回到原值，所以刷机重启后需要在页面里重新切到 3:2。离线 23 项，output/cmos-window11（2e2f975c…），QEMU 三语言固件版本页正常。

实机结果（window11）：显示裁切表两项已改为 1400×848 / 裁 1390、1392×836，取景链仍为 848 行，画面仍只上移。RAM 里显示任务仍有大量 1390/1392×782 → 1920×1080 的副本（如 0xC2346B80、0xC2348A10、0xC234858C），说明显示配置不在进入模式时重读这张表，或另有来源。

用户补充：自从 3:2 预设起作用后，一直有淡条纹，自动对焦失效（Stock 正常）。推测：起始行从 308 改到 106，相位对焦像素行和对应的坏点/对焦像素校正表都按读出窗口内的行号定位，整体错位 202 行，于是对焦像素没被校正（淡条纹），对焦读到的也不是对焦像素（对焦失效）。要修需要同步平移这些表，或找出它们的行偏移参数。

## 下一步

按顺序：

1. **在实机上只读导出驱动数据。** 用 SD 模块宿主或一个诊断补丁，把 `0xC18E4FEC + 0x14` 指向的 0x168000 字节写到 SD 卡。**只读 RAM，绝不写 NOR**——bank 26 里可能混有出厂逐台校准数据，写坏了无法从升级包恢复。导出的数据是 Nikon 数据加个人机身校准，不入库、不分发。
2. **解析 14 个驱动模式。** 对比 4K 30p、1080p 60p、照片取景三种模式的包差异，找出读出窗口（起始行/行数）、跳读/合并、行周期（HMAX）、帧周期（VMAX）对应的寄存器。传感器型号可以从寄存器地址布局反推。
3. **构造 3:2 24p 包。** 以 4K 模式为基础，把窗口扩到全高 3712 行，帧周期按 23.976 fps 重算。用 `0x101401F6` 的钩子在 RAM 里替换包内容。
4. **下游适配（全在 EG 内）。** SIF 采集窗口、`RAWRS` 缩放到 3240×2160（或 16 对齐的 3248×2160）、编码器尺寸、封装器尺寸、实时取景。现有画幅研究里的几何表与选择器可以复用。
5. **实机验证。** 每个测试包都必须仍能进入 设置 → 固件版本 并正常升级。

在第 1 步完成前，第 2–4 步都无法离线推进。
