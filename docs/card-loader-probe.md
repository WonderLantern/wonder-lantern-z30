# SD 卡功能加载：第 0 步 MMU 探测

目标：功能补丁改为开机后从 SD 卡读取并写进 RAM，出问题拔卡即恢复原厂。前提是 EG 代码区（`0x10020000` 起）在运行时能被改写。本页记录静态分析结论和实机探测方法。

## 静态分析（原厂 EG，已确认）

- 开机代码 `0x1002BCF0..0x1002BD14`：TTBR0 = `0x10030000`（页表就在 EG 镜像里），DACR = `0x55555555`（16 个域全部为 client，检查权限），然后打开 MMU、D-cache 和 I-cache。
- 短描述符，1 MiB section，恒等映射（VA = PA）：

| 区域 | 描述符 | 含义 |
| --- | --- | --- |
| `0x10000000..`（EG 代码、tail） | `xxx0C426` | AP=101：特权只读、用户无权限；TEX=4 C=0 B=1：普通可缓存内存；XN=0；域 1 |
| `0xC1800000..`（RAM） | `xxx14426` | AP=001：特权读写；其余属性同上 |
| `0xC8000000..`、`0xD0000000..` | `xxx14422` | AP=001，不可缓存 |

- 代码区和 RAM 用的是同一种内存类型，说明这段很可能是加载器拷到 DRAM 里的副本，而不是原地执行的闪存；但单看镜像无法证明。
- 如果它是 RAM：加载器在特权模式下临时把 DACR 的域 1 设为 manager（`DACR | 0xC`），就能绕过只读权限写入，不需要改页表。
- 任务切换代码 `0x10038BA4`/`0x1004F5A4` 会按任务控制块换 TTBR0，所以页表可能不止一份；探测模块读的是当前任务实际使用的页表。

## 探测模块

`src/z30_extensions/features/research/mmu_probe.py` 生成 `CORE.ZMOD`，由现有 SD 模块宿主加载（ABI 2）。每按一次 Run 显示一行（不超过 24 个字符，中文界面也能完整显示）：

| 行 | 内容 | 预期 |
| --- | --- | --- |
| `1 M=.. S=........` | CPU 模式、SCTLR | M=13/1F 为特权；SCTLR 低位 bit0=1（MMU 开） |
| `2 D=........ C=........` | DACR、TTBCR | D=55555555；C=0 |
| `3 A=........ B=........` | TTBR0、TTBR1 | A 低位去掉后为 10030000 或任务页表 |
| `4 E=........ T=........` | `0x10020000` 与宿主 API 表的 L1 描述符 | `1000C426` / `12xxC426` |
| `5 W=........ R=........` | ATS1CPW / ATS1CPR 对 API 表的 PAR | W 的 bit0=1（写会 fault）、R 的 bit0=0 |
| `6 O=........ V=........` | **唯一的写操作**，见下 | 见判定 |
| `7 F=........` | 恢复后读回 | 必须等于 O |

第 6 行：关中断 → DACR 域 1 设为 manager → 把宿主 API 表里 `get_property` 那个字（位于 EG tail）写成取反值 → 按地址清理并失效该缓存行到 PoC → 从内存读回 V → 写回原值并再次清理 → 恢复 DACR 和中断。第 7 次按完会从第 1 行重新开始。

## 判定

- **V = O 取反、F = O**：写入能到达内存，代码区是 RAM。走计划的主线（分支 A）：卡上补丁文件 + 开机加载器，用 DACR 方式写入。
- **V = O**：写入被丢弃（ROM）。走分支 B（闪存跳板 + RAM tail）。
- **按第 6 次后死机**：多半是写闪存引发的外部中止。拔电池重启；结果按 ROM 处理。
- **第 1 行显示 `USR mode`**：模块运行在用户模式，所有 CP15 操作都做不了，需要换别的入口。

## 实机步骤

1. 生成探测套件（不会写相机或 SD 卡）：

   ```powershell
   python tools/build_mmu_probe.py --source Z_30_0120.bin --output output/mmu-probe
   ```

   相机上已经装着任意一版带 SD 模块宿主的 EG（例如 AF 研究构建）时，只需要模块：

   ```powershell
   python tools/build_mmu_probe.py --zmod-only --output output/mmu-probe
   ```

2. 如需刷 EG：刷完后先确认 **Setup → Firmware version** 能正常进入，固件升级流程正常。
3. 把 `output/mmu-probe/Z30/CORE.ZMOD` 复制到卡上的 `Z30/CORE.ZMOD`。
4. **设置菜单 → 自定义菜单 → SD 卡功能**：Load 一次，显示 `mmu-probe ready`；然后 Run 7 次，记录每一行（拍照最方便）。
5. 取出卡重启，确认相机行为正常。

## 第一版实机读数（2026-11-24）

```text
1 M=13 S=00C5187D   2 D=55555555 C=00000000   3 A=C2AD4000 B=E0AC382A
4 E=CC40C426 T=1210C426   5 W=0000001B R=12127050
6 O=10465985 V=10465985   7 F=10465985
```

- SVC 模式；MMU、缓存开启；DACR 与 TTBCR 同静态分析一致。
- 运行时页表在 RAM（`0xC2AD4000`），不是开机那张。
- **`0x10000000` 段映射到物理 `0xCC400000`（DRAM）**：原厂开机后把 EG 搬进了 DRAM 并重映射。hook 点所在的原厂代码因此位于 RAM。
- tail 所在的 `0x12100000` 段仍是恒等映射。即使域 1 设为 manager，写入也被丢弃（V = O），没有死机。**tail 不可写**。
- 第 5 行：W 为 section 权限 fault（FS=01101），R 正常。

## 第二版探测（原厂代码区写入、DRAM 副本范围）

生成：`python tools/build_mmu_probe.py --zmod-only --output output/mmu-probe-v2`（默认 `--probe 2`），用同一个带模块宿主的 EG。Load 显示 `mmu-probe v2 ready`，Run 5 次：

| 行 | 内容 | 用途 |
| --- | --- | --- |
| `1 A=........ L=........` | TTBR0；从 `0x100` 段起连续搬进 DRAM 的最后一个段号 | 原厂镜像结束在 `0x1207E03A`（段 `0x120`），L 是否覆盖它 |
| `2 N=........ P=........` | 段 L+1 的描述符；VA `0xCC400000` 的描述符 | P 为 `CC414426`（AP=001）即 DRAM 有可写的恒等别名 |
| `3 Q=........ G=........` | 对开机页表一个字 `0x10031000` 做 ATS1CPR 的 PAR；对其 RAM 别名做 ATS1CPW 的 PAR | Q 高 20 位是物理页；G 的 bit0=0 表示别名可写 |
| `4 O=........ V=........` | DACR 方式写 `0x10031000`（取反后读回再恢复） | V = O 取反即原厂代码区可写 |
| `5 V=........ F=........` | 通过 RAM 别名写取反值，再从代码地址读回；F 为恢复后的值 | V = O 取反、F = O：别名写入直接生效，不需要改 DACR；G 不可写时显示 `5 skip` |

`0x10031000` 是开机页表里 VA `0x40000000` 的条目，原值为 0x40000000（fault 类型）。运行时用的是 RAM 页表，这一项也不会被访问，所以写测试不影响相机工作。

## 第二版实机读数（2026-11-24）

```text
1 A=C2AD4000 L=00000106   2 N=1070C426 P=CC414426
3 Q=CC431050 G=CC4310D0   4 O=40000000 V=BFFFFFFF   5 V=BFFFFFFF F=40000000
```

- **只有 `0x10000000..0x106FFFFF`（7 MiB）被搬进 DRAM**（物理 `0xCC400000..0xCCAFFFFF`）。从段 `0x107` 起恢复恒等映射，与 tail 同类；第一版已测得这类段写入被丢弃。
- `0xCC400000` 起的 DRAM 在运行时页表里恒等映射、特权可读写（AP=001）。
- 第 4 行：DACR 方式写原厂代码区成功。第 5 行：通过 DRAM 别名写入，从代码地址读回即生效，恢复正常。**改写前 7 MiB 原厂代码不需要动 DACR**：直接写 `VA - 0x10000000 + 0xCC400000`，然后做缓存维护。

### 各 preset 的改动落在哪里

把每个 preset 单独构建后，和原厂逐字比较（不含 tail），统计改动的字落在哪个区域：

| preset | DRAM 区（<`0x10700000`） | 不可写区 | scatter（开机拷到 RAM） | 不可写区所在页 |
| --- | --- | --- | --- | --- |
| liveview-dual | 107 | 0 | 9 | |
| m900、mtp-fast、focal-length、battery-percent | 2 | 0 | 0 | |
| video-rot | 6 | 0 | 0 | |
| nef-uncompressed / nef-compressed | 9 | 0 | 0 | |
| shutter-sound、gyro-evr、nef-menu | 18～32 | 1 | 3 | `0x1075B000` |
| aspect、zebra、date-stamp、portrait、3d-tracking、af-colour | 21～79 | 2 | 6 | `0x10759000`、`0x1075B000` |
| bitrate-slowmo-uncap | 24 | 18 | 6 | `0x10713000`、`0x1075A000`、`0x1075B000` |

| **full** | **287** | **63** | **18** | 以上全部 |

- 绝大多数 hook 点在可写区。
- 不可写区里的改动集中在少数数据表：`0x1075xxxx` 是声音框架和菜单共用的表，`0x10713xxx` 是码率表，`0x114A3xxx` 是 Wi‑Fi 表。
- tail（约 770 KiB 功能代码）同样位于不可写区。

## 离线验证

`tests/test_mmu_probe.py` 在 Unicorn 中执行两版模块。第一版检查：init 的 ABI 检查、7 行输出格式与长度、L1 描述符读取、写测试读回取反值和恢复原值。第二版检查：段扫描、别名 PAR、两种写测试和恢复。Unicorn 没有开 MMU，也没有真实的闪存或缓存，所以它只证明指令流正确，不说明相机上的结果。
