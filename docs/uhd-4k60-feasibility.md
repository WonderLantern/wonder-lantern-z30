# Z30 C 1.20：4K 50p/60p 解锁可行性与已交付的 4K 码率提升

日期：2026-10-30。全部结论来自本地静态分析与 Unicorn 隔离执行，未修改固件文件、未访问相机；已交付的代码修改可以离线构建并离线验证，但**没有实机测试**。

## 结论

1. **4K 50p/60p 录制目前不能作为固件补丁交付。** 复用空闲模式表行并补上选择器分支只是链条上最容易的两环；决定性的采集管线（传感器读出模式）侧找不到任何 4K 50/60 的读出配置，编码器吞吐是否达到两倍负载无法离线证实，且没有实机测试回路。发布这样的补丁最可能的结局是录出黑屏/丢帧/卡死的素材，且无法远程排查。
2. **已交付 4K 码率提升**：`bitrate-slowmo-uncap` 的机内档位把 4K 30p/25p/24p 高画质从原厂 144/120 Mbps 提高到 **200/168 Mbps**（均衡档 168/140），仍在编码器为 4K 配置的 H.264 Level 5.1 规范码率上限（240 Mbps）之内，机制与已在实机验证过的 1080p 码率解锁完全相同。原厂码率可随时在机内用“原始”档恢复。
3. HEVC 仍不可用（见 [hevc-feasibility.md](hevc-feasibility.md)）；慢动作时长与封装器 125 分钟上限的结论不变（见 [bitrate-slowmo-uncap.md](bitrate-slowmo-uncap.md)）。

## 4K 60p 的证据链

### 原厂模式表与选择器（封装/编码参数层，完全恢复）

模式表 `0x10713154`，30 条 × 0x1C 字节。记录布局（原 [码率说明](bitrate-slowmo-uncap.md) 的“时间基、帧时长、M、N”按 u16/u32 重新核对）：

| 偏移 | 字段 |
| --- | --- |
| +0x00 / +0x02 | 宽 / 高（u16） |
| +0x04 | 时间基（u32）：30000、25000、24000、120000、100000 |
| +0x08 | 帧时长（u32）：1001（NTSC）或 1000（PAL） |
| +0x0C | u32 恒 0 |
| +0x10 / +0x12 | GOP：恒 1 / GOP 长 N（帧） |
| +0x14 / +0x18 | 最大 / 平均码率（u32，bps） |

记录 0–5 为 4K 30p/25p/24p（高画质/标准），6–15 为 1080p 六种帧率，16–19 为 120p/100p，20–23 为菜单里没有的 720p60/50 空闲行，24–29 为慢动作。

选择器 `0x1035566C(mode, out)` 输入 3 字节 `(分辨率码, 帧率码, 画质)`：分辨率码 0=4K、1=1080、2=720；帧率码 0=59.94、1=50、2=29.97、3=25、4=23.976、5=119.88、6=100、7/8/9=慢动作。**4K 分支只映射帧率码 2/3/4；码 0/1（59.94/50）没有分支，落到默认值 6**——固件在参数层就砍掉了 4K 50/60。补这两条分支是平凡的（720p 空闲行 20–23 可改成 4K 59.94/50 记录，表内其余消费方——GOP 读取函数 `0x10355776`、剩余时间估算、封装器配置——都按记录序号自动跟随）。

### 编码器参数构造器实验（`tools/inspect_4k60_encoder.py`）

用 Unicorn 执行原厂构造器 `0x102DFBFE` 与序列化路径（方法与 [hevc-feasibility.md](hevc-feasibility.md) 的深度验证相同）：

| 输入 | 构造出的 level |
| --- | --- |
| 3840×2160，fps 24–120（含 49/59/31 档判别） | **51（Level 5.1）** |
| 1920×1080，fps 29 / 59 / ≥119 | 41 / 50 / 51 |
| 1280×720 | 41 |

配套的 level→MaxMBPS 原厂辅助 `0x102E9DE8` 的完整阶梯：…40→245760、42→522240、50→589824、**51→983040**、**52→2073600**。

两个关键事实：

- **level 阶梯包含 Level 5.2**（2,073,600 MB/s ≈ 530.8 Mpx/s），但**构造器从不输出 52**——4K 无论 24 到 120 fps 一律 51，连超过 5.1 宏块率上限的 4K 31p 输入（需 1,004,400 MB/s）也被压在 51。整个参数栈是按 Level 5.1 封顶构建的。
- 固件里出现 5.2 阶梯值**不能**证明本机硅片能跑到该速率：该辅助可能是跨机型共用库代码。

### 像素率算术（硬件层的边界）

原厂全部录像模式的数据率都顶在同一个值上：4K 30p 与 1080p 120p 都是约 249 Mpx/s，恰好低于 Level 5.1 的 983,040 MB/s × 256 = **251.66 Mpx/s**。4K 60p 需要 **498 Mpx/s，正好是全机已证峰值的 2 倍**，对应 Level 5.2。Z30 的 20.9MP 传感器/ISP 从未在任何模式（包括 120p 慢动作）展示过超过 ~250 Mpx/s 的读出能力。

### 采集管线（决定性缺口）

编码参数层可以照表伪造，但录制开始时采集侧（传感器读出窗口/合并方式/ISP 时序）需要一份 4K@60 的配置。本轮检索（3840/5568/3128/1120 等尺寸值与帧周期常数的共现扫描、`Capture*`/传感器相关字符串、模式选择链上游）**没有找到任何 4K 50/60 读出模式**；此前 [dormant_features](../../analysis/dormant_features/FINDINGS.md) 一轮针对 N-Log、10bit、RAW 视频、4K60 的链路检索也是空结果。传感器读出模式很可能不是 EG 里的平铺数据表（或按计算选择，或依赖下游固件/微码），无法凭现有资料伪造。

### 为什么不发布“实验性 4K60”补丁

- 采集管线层缺配置：最可能的失败是录制启动失败或 60p 容器装 30p 内容，另一可能是编码/写卡路径在两倍负载下卡死。
- 离线验证无法覆盖：没有实机回路时，失败模式无法区分“补丁逻辑错”与“硬件不支持”，也就没有迭代方向。
- 项目已有的实机证据（码率、慢动作、画幅）全部建立在“机制先在离线验证、再有机身复核”的闭环上；4K60 缺了闭环的后一半，也缺了前一半的大头。

若未来要继续，需要按顺序解决：定位传感器读出模式选择代码与配置来源 → 在真机上确认 2 倍像素率下 ISP/编码器行为 → 恢复 UI 帧率菜单的 4K 60p 选项 → 热与续航评估。任一步缺实机都无法闭环。

## 已交付：4K 码率提升（机制实机已证）

| 模式（高画质） | 原始（原厂） | 均衡 | 高质量（默认） |
| --- | --- | --- | --- |
| 4K 30p / 25p / 24p | 144 / 120 | 168 / 140 | **200 / 168** |
| 1080p 60p、50p | 56 / 48 | 84 / 70 | 108 / 90 |
| 1080p 30p、25p、24p | 28 / 24 | 48 / 40 | 72 / 60 |

- 取值依据：4K 由 Level 5.1 构造，其 H.264 规范最大码率为 240 Mbps；200 Mbps 留有余量且不超过规范，与 1080p 解锁（108 Mbps ≤ Level 5.0 的 135 Mbps）同一取舍。码率字段为 u16“最大 kbit/8”，200,000/8 = 25,000 远离 536 Mbps 溢出点。
- 机制与已实机验证的 1080p 码率解锁逐字节相同（同表、同字段、同消费方；运行时三档表已含 4K 行并通过 96 项 Unicorn 逐字节验证）。差异仅是数值提高 39%。
- “原始”档在机内随时恢复原厂码率；未插配置卡时默认“高质量”档。
- 存储要求：200 Mbps ≈ 25 MB/s 持续写入，需 V60 及以上卡速；V30 卡可能掉帧。发热与续航由用户在实机自行确认。
- 未实机测试项：4K 200 Mbps 的实际成片码率与文件完整性、卡速不足行为、剩余时间估算偏差（估算直接读取同一张表，理论上自动跟随）。

python tools/inspect_4k60_encoder.py --source Z_30_0120.bin --output build/research/4k60-encoder.json
