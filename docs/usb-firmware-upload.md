# USB 写入固件文件（fw-upload，设计稿）

日期：2026-11-13；固件：Z30 C 1.20。状态：**设计阶段，尚未实现，未经实机验证。**

## 目标

相机插着 USB 时，电脑把新构建的 `EG209020.BIN` 写进 SD 卡根目录。之后照常在 **设置 → 固件版本** 里刷写，不用再拔插 SD 卡。

要求：

1. USB 中途断开、电脑端程序崩溃或拔线，都不能在根目录留下不完整的 `EG209020.BIN`。
2. 最终文件必须由相机在内部一次完成落地，校验通过才落地。
3. 原厂刷机流程不变：固件版本页能正常打开，刷写方式照旧（见 [verification.md](verification.md) 的固件更新检查）。
4. 只写 SD 卡上的两个固定文件名，不碰 NOR、设置或其他文件。

不在范围内：刷写本身（仍由用户在菜单里确认）、写任意路径、远程触发刷机。

## 总体方案

沿用 `0x9FF1 ReadMemory`（[features/ptp_read.py](../src/z30_extensions/features/ptp_read.py)）的接入方式：在原厂 PTP 操作记录查找 `0x102F8C74` 的包装函数里，为下面几个新操作码返回自有记录，其余操作码仍走原厂查找。

| 操作码 | 名称 | 参数 | 数据阶段 | 作用 |
| --- | --- | --- | --- | --- |
| `0x9FF2` | Begin | 总大小，CRC-32，会话号 | 无 | 新建或截断临时文件，进入接收状态 |
| `0x9FF3` | Chunk | 会话号，偏移 | 电脑 → 相机 | 在偏移处追加一块数据 |
| `0x9FF4` | Commit | 会话号 | 无 | 回读临时文件并校验，通过后落地为最终文件 |
| `0x9FF5` | Abort | 会话号 | 无 | 关闭并删除临时文件，回到空闲 |

`0x9FF1` 保持只读、不变；这个功能可以单独构建，不依赖 `0x9FF1`。但同时构建时，电脑端可以用 `0x9FF1` 读状态块（见“状态块”）。

### 文件

| 文件 | 用途 |
| --- | --- |
| `A:\WL-FWUP.TMP` | 接收中的临时文件，只由 Begin/Chunk 写入 |
| `A:\EG209020.BIN` | 最终文件，只在 Commit 校验通过后出现 |

Commit 落地用 **删除旧 `EG209020.BIN` + 把 `WL-FWUP.TMP` 改名为 `EG209020.BIN`**，不用复制：

- 原厂在 `0x104615E6` 一带就是这个顺序：先 `0x10338460(目标路径)` 删除，成功后 `0x103384F6(源路径, 目标路径)` 改名。两个包装函数都把原始结果转换成原厂的 SUCCESS 码。
- 同一目录内改名只改目录项，不重写数据，所以根目录里的 `EG209020.BIN` 要么是旧文件，要么不存在，要么是完整且校验过的新文件。
- 唯一的中间状态：删除旧文件之后、改名之前断电。这时根目录没有 `EG209020.BIN`，但完整的 `WL-FWUP.TMP` 还在；下次 Commit 可以直接重做（见状态机）。不会出现损坏的最终文件。
- 复制 34 MB 要在 USB 回调里阻塞好几秒，而且复制过程中断仍然会留下半个最终文件，所以不采用。

额外保险：原厂刷写前会检查固件容器自身的 CRC（`container.py` 在主机端用同一个 `crc_hqx` 校验），即使上面的步骤都失效，坏文件也会在刷写前被拒绝。

## 状态机

相机端在 DDR 里放一个固定状态块（见下）。状态：

```
IDLE ──Begin──▶ RECEIVING ──Chunk(偏移=已写)──▶ RECEIVING
                    │                               │
                    │ 已写 = 总大小                  │
                    ▼                               │
                  FULL ──Commit──▶ VERIFYING ──通过──▶ COMMITTED ──▶ IDLE
                    ▲                  │
                    │                  └──不通过──▶ FAILED（删除临时文件）
   任意状态 ──Abort──▶ 删除临时文件 ──▶ IDLE
```

规则：

- **Begin**：会话号由电脑端随机生成，非零。总大小必须在 1 MiB 到 64 MiB 之间（当前构建约 34 MB）。已有会话时 Begin 先关闭并删除旧临时文件，再开始新会话，所以电脑端重启后总能从头再来。
- **Chunk**：只接受顺序写入：偏移必须等于已写字节数，长度大于 0，且偏移 + 长度 ≤ 总大小。偏移小于已写字节数的重发块直接拒绝，不覆盖已写数据。每块写入后：检查短写，更新已写字节数和增量 CRC-32。
- **断点续传**：USB 断开后，临时文件和状态块都还在（相机不断电的话）。电脑端重新连上后先读状态，确认会话号一致，就从“已写字节数”继续发 Chunk。会话号不一致或相机重启过（状态块被清零），就重新 Begin。
- **Commit**：只在 FULL 状态接受，并且增量 CRC 必须等于 Begin 给的 CRC。然后关闭临时文件，**重新打开并从头读一遍**，独立计算 CRC-32 并核对大小。只有回读结果也一致时才删除旧文件并改名。这样能发现写入时报告成功、但卡上数据不对的情况。
- **Commit 分步执行**：回读 34 MB 可能要数秒，放在一次 PTP 回调里可能触发 Windows WPD 超时，也会长时间占住 USB 任务。所以每次 Commit 调用最多回读 8 MiB，未完成时返回 `0x2019 Device Busy`，电脑端循环调用直到返回 OK 或错误。每次调用的耗时要实机测量后再定步长。
- **失败**：任何写入、关闭、回读、CRC、删除或改名失败，都关闭文件句柄并删除临时文件，状态记为 FAILED 和具体原因；最终文件只有在改名那一步才会变化。
- **COMMITTED 之后**：状态回到 IDLE，但保留最后一次结果，方便电脑端确认。

### 删除 / 改名中断后的恢复

Commit 进入“删除旧文件”之前，状态块先记下 RENAMING。如果相机在删除和改名之间重启：

- 状态块已经丢失（DDR 不保留），但卡上有完整的 `WL-FWUP.TMP` 且没有 `EG209020.BIN`。
- 电脑端检测到这种情况时，不尝试“恢复改名”，而是重新 Begin 整个上传。这样相机端不需要保存跨重启的状态，逻辑简单。

## 状态块

固定地址的 DDR 结构，64 字节，相机端独占写入：

| 偏移 | 字段 |
| --- | --- |
| `+0x00` | 魔数 `WLU1` |
| `+0x04` | 版本 |
| `+0x08` | 状态（IDLE / RECEIVING / FULL / VERIFYING / RENAMING / COMMITTED / FAILED） |
| `+0x0C` | 会话号 |
| `+0x10` | 总大小 |
| `+0x14` | 期望 CRC-32 |
| `+0x18` | 已写字节数 |
| `+0x1C` | 增量 CRC-32（写入时） |
| `+0x20` | 已回读字节数 |
| `+0x24` | 回读 CRC-32 |
| `+0x28` | 最后错误码（见下） |
| `+0x2C` | 最后一次文件服务原始返回值 |
| `+0x30` | 临时文件句柄（未打开为 −1） |
| `+0x34` | 保留 |

构建报告（`EG209020.json`）记录状态块地址，电脑端从报告读取，不写死。

## 响应码

| 码 | 含义 |
| --- | --- |
| `0x2001` OK | 操作完成 |
| `0x2019` Device Busy | Commit 尚未回读完，再调用一次 |
| `0x201D` Invalid Parameter | 参数个数、大小范围、会话号或偏移不对；不改变状态 |
| `0x2007` Incomplete Transfer | Chunk 的数据阶段长度不符；不写入 |
| `0x2002` General Error | 文件操作失败或校验不通过；具体原因看状态块 `+0x28` |
| `0x200C` Store Full | 打开或写入时卡满（如果能从文件服务返回值区分） |

错误原因（`+0x28`）：打开失败、写入失败、短写、关闭失败、CRC 不符（写入时）、回读失败、回读 CRC 不符、大小不符、删除失败、改名失败、状态不允许。

## 相机端实现要点

- 新模块 `features/fw_upload.py`，结构参考 `ptp_read.py`：自有操作记录 + 查找包装 + 每个操作码的回调。与 `ptp_read` 同时启用时共用一个查找包装，不能重复替换 `0x102F8C74` 的序言；需要先把包装改成“操作码 → 记录”的小表。
- 文件操作使用已在实机上用过的路径：`0x1033829E` 设路径、`0x103382A2` 打开（创建/截断用 `0x301`，读取用 `0`）、`0x102C8A6A` 写入、`0x10338414` 读取、`0x1033832E` 关闭（[cmos_dump.py](../src/z30_extensions/features/cmos_dump.py)、[sound_settings.py](../src/z30_extensions/features/sound_settings.py)）。删除和改名用上面提到的 `0x10338460`、`0x103384F6`。
- 写入前对缓冲区做 d-cache clean（SD 经 DMA 读取，见 cmos_dump v1 的教训）；回读后在 CPU 读之前做 invalidate 或用新分配的缓冲。
- CRC-32（IEEE 802.3，反射多项式 `0xEDB88320`）用 1 KiB 查找表，表在构建时生成并放进补丁区。
- Chunk 的数据阶段：块大小上限取原厂数据缓冲容量（`0x1045AD50` 返回值）以内，电脑端默认 1 MiB。原厂接收数据阶段的回调顺序和长度获取方式需要先在 Unicorn 里逐项确认，再定代码；这一步是**目前最大的不确定点**。
- 所有文件操作在 PTP 回调所在的任务上下文里执行，不进中断。

## 电脑端工具

新工具 `tools/fw_upload.py`，基于 `tools/ptp_wpd.py` 的 WPD 封装，补上“带数据写入”的 MTP 扩展命令。`ptp_wpd.py` 本身保持只读、不加写入能力。

流程：

1. 本地检查待上传文件：大小在范围内，并用 `container.py` 的逻辑解码并核对容器 CRC，确认是有效的 `EG209020.BIN`。不合格直接拒绝，不连相机。
2. 计算 CRC-32，生成随机会话号，Begin。
3. 按 1 MiB 顺序发 Chunk，显示进度；出错时读状态块决定续传还是重来。
4. 循环 Commit，直到 OK 或错误。
5. 输出结果，提示用户到 **设置 → 固件版本** 刷写。

可选：`--verify` 在 Commit 后用 `0x9FF1`（如果启用）读状态块，再次核对回读 CRC。

## 风险与待确认

| 项 | 说明 | 怎么确认 |
| --- | --- | --- |
| 数据阶段接入 | 原厂电脑 → 相机数据阶段的回调约定尚未完全确认 | Unicorn 中用原厂 SetDevicePropValue `0x1016` 记录对照 |
| Commit 耗时 | 回读 8 MiB 的实际时间，以及 WPD 单条命令的超时 | 实机测量，调整步长 |
| 与相机自身写卡并发 | 拍照、录像时相机也在写卡 | Begin 在录像中或卡忙时拒绝；第一版要求在回放或菜单界面上传 |
| 电脑端缓存 | Windows 的 MTP 文件列表不会显示新文件 | 只影响显示，不影响刷写；文档说明即可 |
| 卡写保护、无卡、卡满 | 打开或写入失败 | Unicorn 注入失败；实机拔卡测试 |
| 与原厂 MTP 会话冲突 | 上传期间资源管理器同时浏览相机 | 实机测试；必要时 Begin 前要求关闭资源管理器窗口 |

## 验证计划

1. **Unicorn（`tools/verify_fw_upload.py`）**
   - 查找：四个新操作码返回自有记录；其余操作码的查找结果与原厂逐个相同（与 `verify_ptp_read.py` 一样遍历）。
   - 正常路径：Begin → 多个 Chunk → 多次 Commit（Busy 后 OK），文件服务夹具里最终只有 `EG209020.BIN`，内容与输入一致。
   - 异常：乱序偏移、重发块、越界、会话号不符、长度为 0、数据阶段不足、短写、写入失败、关闭失败、回读 CRC 不符、删除失败、改名失败、Commit 在 RECEIVING 状态、Abort。每种情况都检查：最终文件没有被改动，临时文件被删除，状态块原因正确。
   - 中断：Chunk 中途停止后，从状态块的已写字节数续传成功。
2. **QEMU**：固件版本页三种语言都能打开原厂页面；真实启动后查找包装对新操作码返回自有记录。
3. **实机**（按顺序，每步通过再继续）：
   1. 只 Begin + Abort，确认卡上不留文件。
   2. 上传一个与卡上现有文件内容相同的构建，用读卡器核对字节一致。
   3. 上传过程中拔 USB，确认根目录 `EG209020.BIN` 未变，重新连接后续传成功。
   4. 上传新构建后在菜单里刷写，确认刷写正常，且新固件里固件版本页和刷写仍然可用。

## 构建

计划作为可单独选择的模块，**不包含在 `full` 中**，直到实机验证完成：

```powershell
python patch.py full fw-upload --source Z_30_0120.bin --output output/EG209020.BIN
```

首次使用仍需要拔一次卡，把带 fw-upload 的构建刷进相机。之后的构建都可以通过 USB 写入；只要新构建里也包含 fw-upload，就可以一直用 USB 更新。
