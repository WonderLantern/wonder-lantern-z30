# 竖拍显示（portrait-ui）

日期：2026-11-13（v19）；固件：Z30 C 1.20。**包含在 `full` 中**，也可单独选择。默认关闭，在 **自定义菜单 → 竖拍显示** 或照片拍摄菜单末尾的直达行打开，选择保存到 `WL-VUI.CFG`。

和其他开关一样，开机后要先进入一次自定义菜单，保存的选择才会恢复；在此之前按关闭处理。

```powershell
python patch.py full --source Z_30_0120.bin --output output/EG209020.BIN
```

- **布局：** 竖拿时照片取景信息按实机坐标重排：顶部两行，底部快门速度、光圈、ISO 一行，左右栏移到竖屏中部。四角对焦框和细线保持原位。

- **实机确认：** 布局、转动后补全（含 USB 计时）、四角红框不残留、横竖来回切换；各测试版都经 设置 → 固件版本 刷入。

## 效果与范围

竖拿相机时，照片取景页的信息改为竖版：

- **顶栏、底栏：** 保持原尺寸，每条拆成两行：左边缘在 x=360 左侧的元素留在原位，其余左移 240 进入第二行；满宽的背景条同时盖住两行。按左边缘判断是因为文字只能按起点定位，图标与其后的文字通常落在同一行。（v1 整排缩到 2/3，实机反馈太小，v2 改为两行。）
- **左栏、右栏和中间元素：** 不缩放，整体平移到竖屏中部；右栏贴右边。
- **全屏元素：** 宽 ≥ 600 且高 ≥ 400 的命令保持原样，例如回放前的黑屏。
- **对焦框：** 红色、绿色元素属于画面，不移动。

以下保持横版：i 菜单和它打开的设置页、从取景页直接打开的设置页（v2，见下）、所有菜单、回放、视频模式、HDMI 输出。

### 诊断读数

“竖拍显示”页的第 3、4 行显示读数。读数只在开关打开、相机竖拿时累积，选择“开启”或“关闭”时清零，换页不清零。各字段都是十六进制：

- `K…`：出现过的界面状态，第 n 位代表状态 n。
- `T…`：出现过的绘制目标，第 n 位代表目标 n。
- `P…`：出现过的界面阶段。
- `B…`：界面忙标志。第 0、1 位表示在取景页（状态 0）见过两个标志非零；第 2、3 位表示在其他界面见过。
- `C…`：720×480 整层贴图用到的目标。
- `R…`：原厂刷新路径经过的次数。
- `F…`：强制全部重画的次数。

## 实现

做法沿用已在 Z 5 实机验证的方案：[honokaoshi83-max/z5-extensions](https://github.com/honokaoshi83-max/z5-extensions) 的 `docs/PORTRAIT_UI.md`。在原厂渲染器的几个绘制入口截住命令，改写位置并旋转 90° 或 270°，原厂界面代码照常运行。

Z30 的渲染器与 Z 5 的相对偏移完全一致：矩形、清除、圆角框和三种图像入口逐一对上。描述符字段也一致：模式在 `+0`，源框在 `+0x10`，目标框在 `+0x18`，角度在 `+0x40`。所有地址都在 Z30 C 1.20 里重新定位，构建时逐字节核对原厂指令。

| 入口 | 地址 | 改写 |
| --- | --- | --- |
| 矩形 | `0x1047743C` | 交换宽高、重算位置；清除入口内部对它的调用（返回 `0x104779CF`）不再转第二次 |
| 清除 | `0x1047797E` | 同上；布局变化后的第一次清除扩大到全屏 |
| 圆角框 | `0x104777FC` | 同上（参数在 r0–r3） |
| 图像 1 | `0x10477C9C` | 改目标框，角度设为 90/270，改用按目标框绘制 |
| 图像 2 | `0x104787F2` | 同图像 1；720×480 的整层复制不改 |
| 图像 3 | `0x10479022` | 不读角度：转换为图像 1 的描述符，经图像 1 绘制后跳过原调用 |
| 文字 | `0x1054E652` | 文字对象的 `vgLoadMatrix`（`0x1050A336`）调用：改字形矩阵 |

**生效条件**（全部满足才改写）：

- 开关打开。
- 朝向函数 `0x1021B5F6` 返回 1 或 2；`video-rot` 也用这个函数。
- 处于照片取景上下文：界面阶段 `0xC181F6FC` 为 1/2，界面状态 `0xC18292AC` 为 0，照片后端 `0xC181B278` 为 1。这与遮幅 v42 经实机确认的条件相同。
- 当前绘制目标 `0xC1808758` 为 2，即屏幕层。

**写法上的约定：**

- 原厂图标的角度字段是 360，按未旋转处理。这是 QEMU 跟踪发现的，Z 5 文档里没有提到。
- 桩代码保存并恢复 r0–r3、r12、lr 和 APSR。被替换的指令原样重放；图像 3 窗口里的 PC 相对加载改为常量。
- 浮点与 24.8 定点之间用整数代码转换，不使用 VFP。

## 与其他功能的关系

| 功能 | 关系 |
| --- | --- |
| 照片画幅的取景遮幅 | 遮幅在 GPU 提交点直接写 UI 下层的取景表面，不经过这些绘制入口，保持画面坐标，不受影响 |
| 原厂网格、参考框 | 网格走硬件网格通道，不受影响 |
| 照片斑马纹 | 走原厂高光通道，不受影响 |

| 视频方向（video-rot） | 共用朝向函数，只读，不冲突 |
| 菜单框架 | 新页 965、文字槽 200–206；不选本功能时，其他所有组合的产物与之前逐字节相同 |

以下都不是实机证据。

- **v2 新增：**

  - 读数只在竖拿时记录。
  - 读数行文字逐字核对。

  - 两个竖拿方向下，6 个入口各 160 例，改写结果与 `portrait_ui.locate` 的 Python 模型一致。
  - 图像 3 经图像 1 转写，160 例。
  - 布局变化后的全屏清除生命周期，6 步。
  - 清除入口内部的矩形调用不会被转两次。
  - 原厂没有任何跳转落入 7 个被替换的指令窗口。
- **开关**（`tools/verify_portrait_ui_switch.py`）：SD 保存与恢复、5 种坏记录都按关闭处理、菜单动作、保存失败。

## v3（2026-11-11）：根据 v2 读数

v2 实机：转动后仍需半按；竖拿时 ISO 等设置仍看不到。三次采集（取景、ISO 设置、直方图页）读数相同：`K00000001 T00003204 P04B0C00003200R00BAF02`。

- **K=1、B=0：** ISO 设置页、直方图页的界面状态都是 0，两个界面忙标志从未非零。设置页无法用这些状态字识别，v2 对设置页的修法因此无效。
- **R=0xBA、F=2：** 刷新路径运行了 186 次，强制请求发出了 2 次，但相机仍需半按。`10453D14` 显示第二个参数才是“重画哪几类内容”（5 位），第三个参数是另一维（推测为屏幕）。v2 只把第三个参数改成 7。
- **T=0x3204、C=0x3200：** 竖拿时用到目标 2、9、12、13；9、12、13 收到 720×480 整层贴图。直方图和设置页可能画在这些离屏层上，本功能目前只改目标 2。

v3 的改动：

- **重绘：** 布局变化后，请求改为 `10453FAC(10453AC3, 0x1F, 7)`，即全部 5 类内容。
- **绘制记录：** 竖拿时记录最近 256 条绘制命令，包括类型、目标、界面状态、阶段、横版位置和调用者。每次打开“竖拍显示”页都会把整块状态写到卡根目录的 `WL-VUI.DBG`（4224 字节），用 `python tools/read_portrait_log.py WL-VUI.DBG` 解码。
- 选择“开启”或“关闭”时，读数和记录一起清零。

## v4（2026-11-11）：去掉强制重绘，按实测坐标排布

**v3 的界面冻结：** 竖拿后半按快门，再转回横拿，画面不再更新，按 DISP 也没有反应。相机本身没有卡死。

USB 实时记录显示：转回横拿时发出了第 4 次强制重绘，即 `10453FAC(10453AC3, 0x1F, 7)`。此后界面任务仍在运行（刷新计数继续增长，但从约每秒 8 次降到约每秒 2 次），而信息层停止更新。QEMU 里单独调用同一请求不会卡，所以推测是它与半按自身的显示流程叠加造成的。v2 只改第三个参数时没有出现冻结。

v4 不再挂 `0x1032431C`，原厂刷新请求恢复为逐字节原样。转动后仍需半按补全，另找办法。

**排布：** 改用按元素的规则表 `portrait_ui.LAYOUT`，依据 USB 读出的取景页真实坐标：

- 顶栏第一行：模式、S、AF-A、AF 区域、OFF 紧凑排在左边，“FINE L”放在这一行的右端。
- 顶栏第二行：其余三个图标左对齐。
- 底栏第一行：测光、快门、光圈、曝光补偿。
- 底栏第二行：ISO 和剩余张数整体居中。
- 规则表没有覆盖的元素仍按分区规则处理。

**实测的其他结论：**

- **直方图：** 在屏幕层上没有任何经过这些入口的绘制，与 Z 5 相同，需要“隐藏原厂直方图、自己画”。
- **竖拿点 ISO：** 竖拿时点 ISO 期间没有出现任何设置页的绘制，说明点击没有被识别。原因是触摸坐标仍按横版判断，需要把触摸坐标反向换算。

## v5–v9（2026-11-11 至 11-13）

- **v5–v6 底栏：** 快门、光圈、ISO 排在最下一行，剩余张数移到上一行右侧。快门显示 1/1000 这类长读数时会多出一个底框（x129–254），按它的整体来划分，不再和光圈叠在一起。OK 提示下移到 y560–606。
- **v6 起，重画请求记录：** 只记录、不改动。结果是转动、半按期间原厂只发周期刷新请求 `10453FAC(.., 3, 1)`，半按引起的全量重画不经过这个函数。
- **v7 起，界面事件记录：** 在 `10310BF8` 等四个分发入口只记录、不改动。实测动作码：`0x13` 半按，`0x00` 松开，`0x49` 在相机转动后约 0.5 秒到达。
- **v8，转动后自动重画：** 动作入口收到 `0x49` 时，先依次派发 `0x13` 和 `0x00`，再交还原厂处理。条件是开关打开、处于照片取景、用户没有正在半按。待实机确认是否补全、是否引起对焦。
- **v9，对焦框残影：** 实测取景页只有 8 种细条清除，就是四角对焦框的 8 条 2 像素线（x68/586–652，y48/390–434），与 Z 5 的发现相同。宽或高不超过 3 像素的清除改为原地执行。原地的框线可能在竖版图标上切出缺口，Z 5 是用缓存的图标补画的，这里暂未做。

## v10–v15（2026-11-13）：转动后自动重画

- **v10–v11，补发半按：** 在周期性的 update 事件里补发界面动作 `0x13`/`0x00`。v11 还会按住约 0.6 秒再松开。实机上补发确实执行了，没有触发对焦，但页面没有重画，所以撤掉。
- **原厂重画机制：** 每个容器的 `+0x9C` 是控件链表。重画遍历 `0x102BD3BA` 对每个“需要重画”标志（`+0x44`）为真的控件调用其绘制函数（`+0x4C`），画完清掉标志。`0x10454226`（`0x102BD4C4`）会把容器内所有控件都置上标志；`0x10454218` 立即遍历，原厂整页刷新 `0x10457274` 就是这两步。
- **v12，找到取景容器：** 遍历记录显示，照片取景里的遍历全部作用于固定全局对象 `0xC2017AB8`（465 个控件，回调 `0x10453AFD`）。原厂固件里有 6 处字面量引用它，都在 `0x10325074`–`0x10327314`。
- **v13，相机卡死：** 在界面事件里调用“全部标脏 + 立即重画”，从横拿转到竖拿时相机卡死。“立即重画”会先进入 `0x10453CCE(10000)` 等待绘制标志，在界面正在处理的事件里自等。
- **v14，QEMU 里崩溃：** 只保留“全部标脏”，在 QEMU 里同样崩溃（取指异常）。465 个控件里有的在当前状态下不能画。
- **v15，只标记画过的控件：** 在遍历调用绘制函数处（`0x102BD3F0`）记下取景容器里原厂实际画过的控件，最多 128 个。转动后只给这些控件置 `+0x44`，交给原厂的下一次遍历去画。离开取景页时清空，回到取景后由原厂重画重新填满。QEMU 里转动全程正常，没有崩溃。由于 QEMU 本身会定期整页重画，补全效果只能靠实机确认。
- **v16，容量 256：** 实机上大部分图标能补全，部分缺失。USB 读数显示 128 条已满，改为 256 条，实测记下 202 个控件。仍有部分图标缺失。
- **v17，同框只画最后一个：** v16 的 202 个控件里有 24 组共用同一个矩形（`+0x10` 的 8 字节相同），例如 `(2,312,38,348)` 有 4 个。原厂只让其中当前显示的那个画，标记全部会让隐藏的控件把可见的图标清掉。每条记录改为（控件，绘制序号），原厂每画一次更新序号；转动后同一矩形只标记序号最大的那个。顶部 AF-A、对焦区域、RAW L 不在共用矩形里，v16 也缺，原因待实机确认。
- **v18，先画背景再画图标：** 在 v17 上用 USB 对比半按前后每个控件的绘制序号，发现转动后 AF-A、RAW L、DX 其实已经重画过，但绘制函数为 `0x104B45DB` 的背景控件只会清空自己的矩形，而它们在链表里排在图标后面，又把图标擦掉了。半按时原厂先画完这些背景，再画图标。v18 也分两步：先标记背景控件，等 4 个更新事件（约 0.8 秒）后再标记其余控件。实机上能补全，但要等一会儿。
- **v19，背景画完就画图标：** 第二步不再固定等待，等第一步标记的背景控件的 `+0x44` 全部被原厂遍历清掉，下一个更新事件就画图标，一般只差一次遍历（约 0.3 秒）。最多等 8 个更新事件。
- **汇编检查：** Keystone 在 `cbz`/`cbnz` 超出 126 字节时不报错，直接回绕成错误目标（v17 初版因此跳进一条 32 位指令中间）。`assembly.assemble` 现在会在每个这样的标签处插入标记重新汇编一次，目标对不上就报错。

## v21（2026-11-15）：i 菜单竖版

做法参照 [WonderLantern/wonder-lantern-z5](https://github.com/WonderLantern/wonder-lantern-z5) 的 `docs/PORTRAIT_UI.md` 与 `src/card_module/vui_card.inc`（按格子编号重排、在光标设置处换向）。Z30 的数据全部在实机上用 v20 研究构建读出。

**为什么不能用 QEMU：** 辅助取景里按动作码 1–0x4F、点 i 按钮、发 17 种硬件按键事件，i 菜单都没有打开（`tools/probe_imenu_qemu.py`）。

**实机读数（USB，`tools/portrait_snap.py` 做内存快照和差异）：**

- 打开 i 菜单后界面状态 `0xC18292AC` 从 0 变为 **3**（与 Z 5 的 UI 模式 3 相同）。阶段、照片后端、两个忙标志不变。
- 横版布局：格子 6×2，每格 120×72，y 280–424；背景 `0,280,720,146`；每格底色矩形 113×66，在 `(4+120c, 284+72r)`，选中项是同一矩形换成黄色；2 像素格线在 x 0/119/239/…/718、y 280/352/424；标题清除 `88,228,544,44`，字形基线 y 264；底栏在 x 463–700、y 430–478。打开菜单期间还会清除几个取景页图标（左上、电池附近）。
- 光标：`0xC182DC54`（块 `0xC182DC4C`+8）、导航块 `0xC201D198`（+0 格数 12，+4 当前格）。右移一次 1→2，下移一次 2→8，即 格号 = 行×6+列。
- 方向键：i 菜单的动作处理 `0x103DEC33` 按事件表分派，右 2、左 3、上 4、下 5（与 Z 5 相同），各自调用 `0x1051B654(方向)`，方向 0 上、1 下、2 右、3 左。导航表状态 `0xC182D8C4` 为 0 时进入 `0x1051B7AC`：读当前格 `0x1042B52A`，按 6×2 算出目标，写导航块 +4，再调光标设置 `0x1042BBFC(格号)` 移动高亮。
- 在格子上按 OK 打开的设置页仍是状态 3，但导航表状态变为 3，导航块格数变为该页选项数（影像品质为 7）。

**改动：**

- **生效条件：** 界面状态 0（取景）或 3（i 菜单）。i 菜单只在导航表状态为 0 时用竖版；设置页按横拿处理（清一次全屏后由原厂横版绘制）。运行字 `R_MODE` 的第 2 位（4）表示 i 菜单，取景与 i 菜单互相切换时各清一次全屏；回到取景后照常用 v19 的标记重画补全。
- **布局（`portrait_ui.locate_menu`）：** 背景 → `0,440,480,216`；格子按格号排成 4×3，第 i 格在第 `i&3` 列、第 `i>>2` 行，竖版格子区 y 440–656；元素按中心确定所在格，2 像素竖线算作所在格的右边线（x 0 是第一格的左边线）；标题左移 120、下移 150；底栏左移 340、下移 240；超过 480 宽的清除按整宽处理。不属于菜单的清除不执行（宽高置 0），以免在菜单上打洞。i 菜单里不用“细条清除留在原位”的规则（那是取景页对焦框专用）。
- **方向键（`portrait_ui.nav_target`）：** 挂钩 `0x1051B654` 入口（10 字节窗口）。开关打开、`R_MODE` 带 i 菜单位、界面状态 3、导航表状态 0、格数 12、方向 0–3 时：把物理方向按朝向转成竖屏方向，在 4×3 内移动（行内、列内循环），写导航块 +4，调 `0x1042BBFC`，返回；否则重放原指令走原厂路径。

**已知限制：**

- 竖版格子 4、8（第 2、3 行第 1 格）的左边线缺失：横版里它们左侧没有自己的格线。该线贴着屏幕左缘，影响很小。
- 方向键不跳过不可用的格子（原厂 6×2 会跳过）；会停在灰色格上。
- 设置页、竖拿时的触摸仍为横版。

## v22（2026-11-15）：竖拍触控和设置页

做法参照 [WonderLantern/wonder-lantern-z5](https://github.com/WonderLantern/wonder-lantern-z5) `docs/PORTRAIT_UI.md` 第 12.1–12.2 节（Z 5 第 104–117 组）。Z30 的入口全部重新定位。

### 触摸入口（离线分析 + QEMU）

- 拍摄程序的循环收到事件 `0x56` 时（`0x102F7678`），界面状态 < `0x11` 调 `0x104F1AD4`（相当于 Z 5 的入口 C，原厂开头字节与 Z 5 相同），否则调 `0x1039DA3C`（入口 D）。取景页（0）和 i 菜单（3）都走入口 C。
- `0x104F1AD4(事件)` 复制 60 字节事件后分给各控件；控件再经 `0x10456220` 把事件复制到全局 `0xC2006558`，i 菜单的格子命中（`0x103D2F18`，按 `行×6+列` 算格号）读的就是这份。所以在入口 C 就地改写事件，后面所有读者都看到换算后的坐标。
- 事件格式与 Z 5 相同：`+8` 接触（1 按下、0 抬起），`+9` 类型（1 点按、2 移动、3 拖动结束、4 按住、9 取消），`+0x12/+0x14` 横版面板坐标。原厂取消事件（`0x104F1CC6`）也经过入口 C。
- 菜单用 GUI 自己的入口 `0x104759DC`（QEMU 里点菜单行时经主循环 `0x103CF766` 到达），本版不改。
- **QEMU：** 辅助取景里注入的触摸不会进拍摄循环（和 v21 打不开 i 菜单是同一个限制）。直接调用入口 C 并传入“点 i 按钮”的事件，原厂把它分给了控件处理 `0x10456AEE`，并复制进 `0xC2006558`；i 菜单仍未打开。

### 触摸换算

- 生效条件同绘制：开关打开、竖拿、照片取景上下文（`R_MODE` 不为 0）。横拿、倒置、开关关闭时，事件逐字节不变。
- 竖屏上的点：手柄朝下（2）`px = 480 − Y, py = X`；手柄朝上（1）`px = Y, py = 720 − X`。
- **按下时决定整次触摸**（按下 → 拖动 → 抬起沿用同一换算，直到抬起、拖动结束或原厂取消）：
  - **取景页：** 6 个控件（触摸快门按钮、i 按钮、提示按钮、快门、光圈、ISO），横版位置取自 USB 读出的取景页坐标，竖版位置由 `portrait_locate` 算出。按在竖版控件上，点换回该控件的横版位置。按在这些控件的横版原位置（竖拿时那里已经空了）：整次触摸改成取消。其他位置（取景画面上的触摸对焦等）不变。
  - **i 菜单：** 12 个格子按 4×3 → 6×2 逆算；底栏按 `MENU_BAR` 逆算。其他位置取消。
  - **设置页（2/3）：** 页面内的点按 3/2 精确逆算（`X = px×3/2`，`Y = (py − 400)×3/2`）；页面上方取消。
- 换算后的坐标限制在 0–719、0–479。
- 研究构建记录竖拿时的每个触摸事件（最近 64 个：换算前后的点、类型、接触、界面状态、触摸状态、布局模式），`python tools/portrait_live.py --report … touches` 读出。

### 设置页

- i 菜单格子上按 OK 打开的设置页（界面状态 3、导航表状态不为 0）：Z30 的设置页布局还没读出，本版不逐项排布，而是整页按 2/3（`(v×683)>>10`）缩小、转正，放在竖屏下部（480×320，y 400–720）。字形矩阵同样缩小。全屏元素（宽 ≥ 600 且高 ≥ 400）不变。
- 进出设置页时 `R_MODE` 改变，照常清一次全屏。
- **方向键：** 设置页的方向键以动作码到达 `0x10310BF8`（右 2、左 3、上 4、下 5，i 菜单处理 `0x103DEC33` 读取）。2/3 模式下在已有的动作入口里按朝向改写动作码，换向表由 v21 实机验证过的 `NAV_TURN` 推出：手柄朝上时 右→上、左→下、上→左、下→右；手柄朝下时 右→下、左→上、上→右、下→左。

### 离线验证

- Unicorn（`tools/verify_portrait_ui.py`，`portrait-ui` 和 `full portrait-ui` 各一遍，0 失败）：
  - 设置页：两个朝向下 6 个入口各 120 例与 `locate_mini` 一致；进入设置页时清一次全屏，`R_MODE` 带 2/3 位。
  - 触摸：三种布局 × 两个朝向，每个控件的中心和两角、横版原位置、24 个随机点，各带随机拖动和抬起，加一次原厂取消，共 1119 个事件。事件、触摸状态、记录都与 `touch_map` 一致。开关关闭、无状态块、横拿、横拿设置页共 96 例，寄存器、栈、事件与原厂窗口相同。

- 单元测试 145 项通过。

3. 竖拿滑条页上点 ◀◀、◀、▶、▶▶：数值应按屏幕方向变化；点底栏另一项应切到它的滑条页；点画面应与原厂相同（多半关闭滑条页）。
4. 竖拿滑条页上用方向键：按屏幕上的左右改数值。
5. 关闭滑条页后取景页竖版完整，没有残影；横竖来回转动，页面跟着变。
6. 出问题时拍照，运行 `python tools/portrait_live.py --report <构建>.json touches` 和 `status`。

## 直方图（v24–v26，2026-11-17）

竖拿时原厂直方图仍在横版位置（实机）。Z30 的直方图和 Z 5 一样不经过任何绘制入口（见 v4 读数），所以按 Z 5 的做法（[wonder-lantern-z5](https://github.com/WonderLantern/wonder-lantern-z5) `docs/PORTRAIT_UI.md` 第 5、6 节）：竖拿时隐藏原厂直方图，自己读数据画竖版。

### 实机读数（v23 研究构建，USB `0x9FF1`）

- **数据：** 256 档亮度计数（每档 32 位）在 **`0xC201768C`**，另一份相同的在 **`0xC2018EF0`**（两者偶尔差一帧，一份由另一份复制）。总数恒为 92928（采样像素数）。亮场景平均第 248 档、末档 39885；盖镜头平均第 5 档。方法：亮、暗场景各转储 `0xC2000000` 和 `0xC1800000` 起各 1 MB，找 256 字总数相同、分布相反的数组（转储在 `build/research/hist/`）。还没在固件里找到引用它们的代码。
- **何时更新：** 只在直方图页（DISP 状态 `0xC2016BFE` = 2）更新，竖拿时照常更新；切到非直方图页数据停住。与 `liveview-dual` 的取数判断一致（DISP 2、3、5 放行）。
- **重启：** 关机再开，两个地址不变，数据照常更新。
- **显示掩码：** 描述符 `0xC1826714` 的 9 个掩码在 RAM `0xC1826718` 起，带 `liveview-dual` 时为 `0xCCC`（原厂 `0x444`）；描述符第一个字 RAM 里为 1（ROM 为 0）。

- **时钟：** `0xC18EB098` 是内核的 64 位毫秒时间（调度代码用 `ldrd` 读），取低 32 位限频。三次转储对比，增速 0.999。
- **竖拿时的原厂直方图（USB 截图）：** 仍横着画在竖屏左下（x 110–207、y 475–675），即横版约 (475,273,200,97)。

### 做法（v24）

1. **隐藏原厂（`portrait_hmask`）：** 每个绘制命令进钩子时检查：开关打开、竖拿、取景页布局（不是 i 菜单、设置页、滑条页）、DISP 状态 `0xC2016BFE` = 2，满足就把 9 个掩码存进状态块再清零；不满足就恢复。Z30 的取数判断看 DISP 状态而不是掩码（`1044FF70`、`1036E8B4`），所以预计不会有 Z 5 第 3 位那样的冲突。
2. **自己画（`portrait_hist`）：** 在屏幕层的清除命令处、该命令换到竖版位置之后执行。至少隔 80 ms 读一次 256 档；每 4 档合成一根柱，共 64 根，每根 3 像素宽，整块 192×96，放在竖屏 (236,144)（i 按钮之上、对焦区清除框之上、曝光标尺左边）。峰值取最大值和 4 倍平均值中较小的一个。第一次和被盖过之后整块重画（清除、半透明黑底 `0x00000080`、柱 `0xE6E6E6FF`、三条分隔线和白框）；之后只重画高度变了的柱。
3. **不被原厂清除盖掉：** 当前清除命令（已换到竖版位置）如果和直方图框重叠，这次不画，标记为脏，下一次整块重画。
4. **擦除：** 离开直方图页或打开 i 菜单、设置页、滑条页时清掉一次；转动或换手柄方向时，原有的整屏清除会把它一起清掉，之后重画。
5. **直通调用：** 自己的矩形和清除经过两个直通入口（重放原厂开头几条指令后跳回原厂函数体），不经过竖拍钩子。描述符 x、y（朝上）、w、h、颜色，+0x14 圆角、+0x18/+0x19 混合模式都为 0，与 Z 5 相同。
6. **读数：** `portrait_live.py status` 新增 `histogram` 一项：当前画在哪个手柄方向、是否脏、整块和局部重画次数、被盖次数、掩码是否已隐藏、保存的和当前的掩码、DISP、时钟、64 根柱的高度。

### 离线验证（v24）

## USB 实时读取（研究构建）

`tools/build_portrait_live.py` 构建 `full` + `portrait-ui`，并加上只读的 USB PTP 操作 `0x9FF1 ReadMemory`（`features/ptp_read.py`）。这个操作在 CMOS 研究里已经实机用过：2026-11-04 连续读 120 秒，没有丢失。

相机用 USB 连电脑，开机后先进一次自定义菜单（建立状态块），然后运行：

```powershell
python tools/build_portrait_live.py --source Z_30_0120.bin --output output/portrait-ui-live/EG209020.BIN
python tools/portrait_live.py --report output/portrait-ui-live/EG209020.json status
python tools/portrait_live.py --report output/portrait-ui-live/EG209020.json follow --seconds 120 --out build/research/portrait-live.jsonl
python tools/portrait_layout_from_log.py build/research/portrait-live.jsonl
```

- `status`：读数和上下文字（界面状态、阶段、绘制目标、两个忙标志、姿态字）。
- `follow`：边操作边输出新的绘制记录和上下文变化。
- `portrait_layout_from_log.py`：把取景页每个元素的横版坐标按区域整理出来，用来写逐元素布局表。

实机照片（v3，竖拿）显示方向正确，图标、文字、底框一起旋转，但通用分区的排布不整齐：顶部第一行左侧单独一个模式图标；“FINE L”单独挂在右上；底部 ISO 和剩余张数挤在右边缘。下一步用实时记录的真实坐标改成逐元素布局。
