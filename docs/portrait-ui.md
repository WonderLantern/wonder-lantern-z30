# 竖拍显示（portrait-ui）

日期：2026-11-13（v19）；固件：Z30 C 1.20。**包含在 `full` 中**，也可单独选择。默认关闭，在 **自定义菜单 → 竖拍显示** 或照片拍摄菜单末尾的直达行打开，选择保存到 `WL-VUI.CFG`。

和其他开关一样，开机后要先进入一次自定义菜单，保存的选择才会恢复；在此之前按关闭处理。

```powershell
python patch.py full --source Z_30_0120.bin --output output/EG209020.BIN
```

## 当前状态（v19）

- **布局：** 竖拿时照片取景信息按实机坐标重排：顶部两行，底部快门速度、光圈、ISO 一行，左右栏移到竖屏中部。四角对焦框和细线保持原位。
- **转动后自动补全：** 不用半按。相机报告新方向后，先重画背景控件，背景画完后再重画图标和文字；实机计时约 0.3–0.5 秒。之前还要等相机自己确认方向，这一段由原厂决定。
- **实机确认：** 布局、转动后补全（含 USB 计时）、四角红框不残留、横竖来回切换；各测试版都经 设置 → 固件版本 刷入。
- **仍为横版或未做：** i 菜单和它打开的设置页、从取景页触摸打开的设置页（竖拿时触摸位置没有换算）、直方图、菜单、回放、视频模式、HDMI 输出。
- **正式构建不含诊断：** 菜单页只有 OFF/ON，不写 `WL-VUI.DBG`。研究构建（`tools/build_portrait_live.py`，调用 `portrait_menu.set_diagnostics(True)` 并加上 USB 读取）才显示两行读数并在打开页面时导出状态块。

## 效果与范围

竖拿相机时，照片取景页的信息改为竖版：

- **顶栏、底栏：** 保持原尺寸，每条拆成两行：左边缘在 x=360 左侧的元素留在原位，其余左移 240 进入第二行；满宽的背景条同时盖住两行。按左边缘判断是因为文字只能按起点定位，图标与其后的文字通常落在同一行。（v1 整排缩到 2/3，实机反馈太小，v2 改为两行。）
- **左栏、右栏和中间元素：** 不缩放，整体平移到竖屏中部；右栏贴右边。
- **全屏元素：** 宽 ≥ 600 且高 ≥ 400 的命令保持原样，例如回放前的黑屏。
- **对焦框：** 红色、绿色元素属于画面，不移动。

以下保持横版：i 菜单和它打开的设置页、从取景页直接打开的设置页（v2，见下）、所有菜单、回放、视频模式、HDMI 输出。

### 诊断读数

“竖拍显示”页的第 3、4 行显示读数。读数只在开关打开、相机竖拿时累积，选择“开启”或“关闭”时清零，换页不清零。各字段都是十六进制：

- `K…`：出现过的界面状态，第 n 位代表状态 n。
- `T…`：出现过的绘制目标，第 n 位代表目标 n。
- `P…`：出现过的界面阶段。
- `B…`：界面忙标志。第 0、1 位表示在取景页（状态 0）见过两个标志非零；第 2、3 位表示在其他界面见过。
- `C…`：720×480 整层贴图用到的目标。
- `R…`：原厂刷新路径经过的次数。
- `F…`：强制全部重画的次数。

## 实现

做法沿用已在 Z 5 实机验证的方案：[honokaoshi83-max/z5-extensions](https://github.com/honokaoshi83-max/z5-extensions) 的 `docs/PORTRAIT_UI.md`。在原厂渲染器的几个绘制入口截住命令，改写位置并旋转 90° 或 270°，原厂界面代码照常运行。

Z30 的渲染器与 Z 5 的相对偏移完全一致：矩形、清除、圆角框和三种图像入口逐一对上。描述符字段也一致：模式在 `+0`，源框在 `+0x10`，目标框在 `+0x18`，角度在 `+0x40`。所有地址都在 Z30 C 1.20 里重新定位，构建时逐字节核对原厂指令。

| 入口 | 地址 | 改写 |
| --- | --- | --- |
| 矩形 | `0x1047743C` | 交换宽高、重算位置；清除入口内部对它的调用（返回 `0x104779CF`）不再转第二次 |
| 清除 | `0x1047797E` | 同上；布局变化后的第一次清除扩大到全屏 |
| 圆角框 | `0x104777FC` | 同上（参数在 r0–r3） |
| 图像 1 | `0x10477C9C` | 改目标框，角度设为 90/270，改用按目标框绘制 |
| 图像 2 | `0x104787F2` | 同图像 1；720×480 的整层复制不改 |
| 图像 3 | `0x10479022` | 不读角度：转换为图像 1 的描述符，经图像 1 绘制后跳过原调用 |
| 文字 | `0x1054E652` | 文字对象的 `vgLoadMatrix`（`0x1050A336`）调用：改字形矩阵 |

**生效条件**（全部满足才改写）：

- 开关打开。
- 朝向函数 `0x1021B5F6` 返回 1 或 2；`video-rot` 也用这个函数。
- 处于照片取景上下文：界面阶段 `0xC181F6FC` 为 1/2，界面状态 `0xC18292AC` 为 0，照片后端 `0xC181B278` 为 1。这与遮幅 v42 经实机确认的条件相同。
- 当前绘制目标 `0xC1808758` 为 2，即屏幕层。

**写法上的约定：**

- 原厂图标的角度字段是 360，按未旋转处理。这是 QEMU 跟踪发现的，Z 5 文档里没有提到。
- 桩代码保存并恢复 r0–r3、r12、lr 和 APSR。被替换的指令原样重放；图像 3 窗口里的 PC 相对加载改为常量。
- 浮点与 24.8 定点之间用整数代码转换，不使用 VFP。

## 与其他功能的关系

| 功能 | 关系 |
| --- | --- |
| 照片画幅的取景遮幅 | 遮幅在 GPU 提交点直接写 UI 下层的取景表面，不经过这些绘制入口，保持画面坐标，不受影响 |

## v3（2026-11-11）：根据 v2 读数

v2 实机：转动后仍需半按；竖拿时 ISO 等设置仍看不到。三次采集（取景、ISO 设置、直方图页）读数相同：`K00000001 T00003204 P04B0C00003200R00BAF02`。

- **K=1、B=0：** ISO 设置页、直方图页的界面状态都是 0，两个界面忙标志从未非零。设置页无法用这些状态字识别，v2 对设置页的修法因此无效。
- **R=0xBA、F=2：** 刷新路径运行了 186 次，强制请求发出了 2 次，但相机仍需半按。`10453D14` 显示第二个参数才是“重画哪几类内容”（5 位），第三个参数是另一维（推测为屏幕）。v2 只把第三个参数改成 7。
- **T=0x3204、C=0x3200：** 竖拿时用到目标 2、9、12、13；9、12、13 收到 720×480 整层贴图。直方图和设置页可能画在这些离屏层上，本功能目前只改目标 2。

v3 的改动：

- **重绘：** 布局变化后，请求改为 `10453FAC(10453AC3, 0x1F, 7)`，即全部 5 类内容。
- **绘制记录：** 竖拿时记录最近 256 条绘制命令，包括类型、目标、界面状态、阶段、横版位置和调用者。每次打开“竖拍显示”页都会把整块状态写到卡根目录的 `WL-VUI.DBG`（4224 字节），用 `python tools/read_portrait_log.py WL-VUI.DBG` 解码。
- 选择“开启”或“关闭”时，读数和记录一起清零。

## v4（2026-11-11）：去掉强制重绘，按实测坐标排布

**v3 的界面冻结：** 竖拿后半按快门，再转回横拿，画面不再更新，按 DISP 也没有反应。相机本身没有卡死。

USB 实时记录显示：转回横拿时发出了第 4 次强制重绘，即 `10453FAC(10453AC3, 0x1F, 7)`。此后界面任务仍在运行（刷新计数继续增长，但从约每秒 8 次降到约每秒 2 次），而信息层停止更新。QEMU 里单独调用同一请求不会卡，所以推测是它与半按自身的显示流程叠加造成的。v2 只改第三个参数时没有出现冻结。

v4 不再挂 `0x1032431C`，原厂刷新请求恢复为逐字节原样。转动后仍需半按补全，另找办法。

**排布：** 改用按元素的规则表 `portrait_ui.LAYOUT`，依据 USB 读出的取景页真实坐标：

- 顶栏第一行：模式、S、AF-A、AF 区域、OFF 紧凑排在左边，“FINE L”放在这一行的右端。
- 顶栏第二行：其余三个图标左对齐。
- 底栏第一行：测光、快门、光圈、曝光补偿。
- 底栏第二行：ISO 和剩余张数整体居中。
- 规则表没有覆盖的元素仍按分区规则处理。

**实测的其他结论：**

- **直方图：** 在屏幕层上没有任何经过这些入口的绘制，与 Z 5 相同，需要“隐藏原厂直方图、自己画”。
- **竖拿点 ISO：** 竖拿时点 ISO 期间没有出现任何设置页的绘制，说明点击没有被识别。原因是触摸坐标仍按横版判断，需要把触摸坐标反向换算。

## v5–v9（2026-11-11 至 11-13）

- **v5–v6 底栏：** 快门、光圈、ISO 排在最下一行，剩余张数移到上一行右侧。快门显示 1/1000 这类长读数时会多出一个底框（x129–254），按它的整体来划分，不再和光圈叠在一起。OK 提示下移到 y560–606。
- **v6 起，重画请求记录：** 只记录、不改动。结果是转动、半按期间原厂只发周期刷新请求 `10453FAC(.., 3, 1)`，半按引起的全量重画不经过这个函数。
- **v7 起，界面事件记录：** 在 `10310BF8` 等四个分发入口只记录、不改动。实测动作码：`0x13` 半按，`0x00` 松开，`0x49` 在相机转动后约 0.5 秒到达。
- **v8，转动后自动重画：** 动作入口收到 `0x49` 时，先依次派发 `0x13` 和 `0x00`，再交还原厂处理。条件是开关打开、处于照片取景、用户没有正在半按。待实机确认是否补全、是否引起对焦。
- **v9，对焦框残影：** 实测取景页只有 8 种细条清除，就是四角对焦框的 8 条 2 像素线（x68/586–652，y48/390–434），与 Z 5 的发现相同。宽或高不超过 3 像素的清除改为原地执行。原地的框线可能在竖版图标上切出缺口，Z 5 是用缓存的图标补画的，这里暂未做。

## v10–v15（2026-11-13）：转动后自动重画

- **v10–v11，补发半按：** 在周期性的 update 事件里补发界面动作 `0x13`/`0x00`。v11 还会按住约 0.6 秒再松开。实机上补发确实执行了，没有触发对焦，但页面没有重画，所以撤掉。
- **原厂重画机制：** 每个容器的 `+0x9C` 是控件链表。重画遍历 `0x102BD3BA` 对每个“需要重画”标志（`+0x44`）为真的控件调用其绘制函数（`+0x4C`），画完清掉标志。`0x10454226`（`0x102BD4C4`）会把容器内所有控件都置上标志；`0x10454218` 立即遍历，原厂整页刷新 `0x10457274` 就是这两步。
- **v12，找到取景容器：** 遍历记录显示，照片取景里的遍历全部作用于固定全局对象 `0xC2017AB8`（465 个控件，回调 `0x10453AFD`）。原厂固件里有 6 处字面量引用它，都在 `0x10325074`–`0x10327314`。
- **v13，相机卡死：** 在界面事件里调用“全部标脏 + 立即重画”，从横拿转到竖拿时相机卡死。“立即重画”会先进入 `0x10453CCE(10000)` 等待绘制标志，在界面正在处理的事件里自等。
- **v14，QEMU 里崩溃：** 只保留“全部标脏”，在 QEMU 里同样崩溃（取指异常）。465 个控件里有的在当前状态下不能画。
- **v15，只标记画过的控件：** 在遍历调用绘制函数处（`0x102BD3F0`）记下取景容器里原厂实际画过的控件，最多 128 个。转动后只给这些控件置 `+0x44`，交给原厂的下一次遍历去画。离开取景页时清空，回到取景后由原厂重画重新填满。QEMU 里转动全程正常，没有崩溃。由于 QEMU 本身会定期整页重画，补全效果只能靠实机确认。
- **v16，容量 256：** 实机上大部分图标能补全，部分缺失。USB 读数显示 128 条已满，改为 256 条，实测记下 202 个控件。仍有部分图标缺失。
- **v17，同框只画最后一个：** v16 的 202 个控件里有 24 组共用同一个矩形（`+0x10` 的 8 字节相同），例如 `(2,312,38,348)` 有 4 个。原厂只让其中当前显示的那个画，标记全部会让隐藏的控件把可见的图标清掉。每条记录改为（控件，绘制序号），原厂每画一次更新序号；转动后同一矩形只标记序号最大的那个。顶部 AF-A、对焦区域、RAW L 不在共用矩形里，v16 也缺，原因待实机确认。
- **v18，先画背景再画图标：** 在 v17 上用 USB 对比半按前后每个控件的绘制序号，发现转动后 AF-A、RAW L、DX 其实已经重画过，但绘制函数为 `0x104B45DB` 的背景控件只会清空自己的矩形，而它们在链表里排在图标后面，又把图标擦掉了。半按时原厂先画完这些背景，再画图标。v18 也分两步：先标记背景控件，等 4 个更新事件（约 0.8 秒）后再标记其余控件。实机上能补全，但要等一会儿。
- **v19，背景画完就画图标：** 第二步不再固定等待，等第一步标记的背景控件的 `+0x44` 全部被原厂遍历清掉，下一个更新事件就画图标，一般只差一次遍历（约 0.3 秒）。最多等 8 个更新事件。
- **汇编检查：** Keystone 在 `cbz`/`cbnz` 超出 126 字节时不报错，直接回绕成错误目标（v17 初版因此跳进一条 32 位指令中间）。`assembly.assemble` 现在会在每个这样的标签处插入标记重新汇编一次，目标对不上就报错。

## USB 实时读取（研究构建）

`tools/build_portrait_live.py` 构建 `full` + `portrait-ui`，并加上只读的 USB PTP 操作 `0x9FF1 ReadMemory`（`features/ptp_read.py`）。这个操作在 CMOS 研究里已经实机用过：2026-11-04 连续读 120 秒，没有丢失。

相机用 USB 连电脑，开机后先进一次自定义菜单（建立状态块），然后运行：

```powershell
python tools/build_portrait_live.py --source Z_30_0120.bin --output output/portrait-ui-live/EG209020.BIN
python tools/portrait_live.py --report output/portrait-ui-live/EG209020.json status
python tools/portrait_live.py --report output/portrait-ui-live/EG209020.json follow --seconds 120 --out build/research/portrait-live.jsonl
python tools/portrait_layout_from_log.py build/research/portrait-live.jsonl
```

- `status`：读数和上下文字（界面状态、阶段、绘制目标、两个忙标志、姿态字）。
- `follow`：边操作边输出新的绘制记录和上下文变化。
- `portrait_layout_from_log.py`：把取景页每个元素的横版坐标按区域整理出来，用来写逐元素布局表。

实机照片（v3，竖拿）显示方向正确，图标、文字、底框一起旋转，但通用分区的排布不整齐：顶部第一行左侧单独一个模式图标；“FINE L”单独挂在右上；底部 ISO 和剩余张数挤在右边缘。下一步用实时记录的真实坐标改成逐元素布局。

## 实机测试计划（首次）

刷入前先确认能回到原厂，这是唯一的退路：设定 → 固件版本能打开，并且能用原厂固件更新。

1. **默认关闭：** 横拿、竖拿各看一次取景页，应与原厂完全相同。确认固件版本页能打开。
2. **打开开关：** 进入 自定义菜单 → 竖拍显示 → 开启，回到取景页。
3. **横拿：** 画面应与原厂相同。
4. **两侧竖拿：** 手柄朝上、手柄朝下各拍一张背屏照片。重点看这几项：
   - 信息是否是正的。如果两侧都**上下颠倒**，说明朝向 1/2 与物理方向对应反了，需要交换。
   - 顶栏和底栏的文字是否清楚。
   - 有没有元素留在横版位置、或者出现残影。
5. **转动后的重画：** 转动后如果有信息缺失，半按一次快门或按 DISP 看能否补全。原厂不会因为转动而重画；本版只在转动后擦一次屏幕，没有像 Z 5 那样模拟半按。
6. **i 菜单：** 竖拿时打开、关闭 i 菜单，菜单本身应为横版，关闭后取景信息应恢复竖版。
7. **各 DISP 页、放大取景、拨盘调整曝光：** 调整时的数值显示是否正常。全信息页上要看水平仪。
8. **其他功能：** 打开照片画幅遮幅时竖拿，遮幅和网格应保持在画面上；回放旧照片应不受影响。
9. **切换功能：** 关闭开关后回到取景页，应完全回到原厂。

如果出现异常，请拍下背屏照片，并注明当时手柄朝上还是朝下、在哪个 DISP 页。布局的分区参数（顶栏、底栏、左右栏的边界和平移量）在 `portrait_ui.py` 开头，可以按照片调整。
